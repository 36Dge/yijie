# 连接器接入三种原生审批模式的实施方案

2026-11-22 · FEAT-157 · local / demo_fast · 实施进度见[本地实施记录](26-native-approval-implementation-2026-11-22.md)

**用户结果。** 用户在「帮我批准」或已确认的「完全访问」下选择 Sorftime，可以直接发送查询。在「请求批准」下，具备相应原生能力的工具提供「允许一次」「本会话允许此工具」「始终允许此工具」。保留「拒绝」和「取消本次」。工具、账号、操作和授权期限要能在界面上看清。

**实现决定。** 由 `yijie-codex` 决定是否询问、如何自动审核、如何应用和撤销记忆。Desktop 显示该笔请求实际提供的选项。Host 把真实原生结果关联到 Worker 登记的调用，Worker 继续检查本轮选集和业务权限并签发一次性发送许可。方案沿用 Broker 0.9.0 与 Runtime 0031 的续期及终止行为。[现状与实跑证据](24-connector-execution-audit-2026-11-22.md) · [已接受的权限边界](../../adr/ADR-0021-local-market-connector-authority.md)

## 用户会遇到什么

| 权限模式 | 普通、已准入的连接器调用 | 拒绝、受限操作与记忆 |
| --- | --- | --- |
| 请求批准 | 没有适用记忆时，显示实际连接器、工具、影响范围和参数。主按钮允许一次。下拉仅展示原生提供且本次业务规则允许的会话／长期选项。命中有效记忆后直接进入本次调用校验。 | 拒绝或取消结束本次调用。要求逐次确认的操作仅提供单次决定。 |
| 帮我批准 | 使用原生 `on-request + auto_review`，由 Guardian 处理符合自动审核条件的 MCP 请求。原生允许后继续，用户可在记录中看到「自动审核通过」。 | 原生拒绝或超时结束本次尝试。可由本人接管的拒绝沿用现有原生卡片。接管针对明确动作，已结束的调用不能因接管而复活。 |
| 完全访问 | 使用已确认的 `never + dangerFullAccess`。对本轮已选、有效且业务策略允许直接执行的工具，使用原生无交互路径；普通查询没有逐次确认卡。 | 继续执行供应商 scope 和业务审批规则。改价、改库存、广告预算等已有强制审批要求的操作走既有业务审批；缺少该能力时在调用点明确阻止。 |

**Sorftime 排行榜的验收口径。** 三种模式都应允许发送这条消息。能否返回销量榜取决于当前安装实际发现的工具、账号权限和供应商提供的数据。通用适配目前把未知效果按写入风险处理。实施时先从已核准的 Sorftime 工具定义确认真实方法、schema 及只读范围，把可自动执行的查询纳入现有供应商工具策略，保留参数校验。产品不能根据“最近一周销量”这样的提示词给工具降风险。若某个方法缺少资格，提示应指向该方法，避免用整轮强制切回 ask 掩盖原因。[通用工具校验](../../../../yijie-connectors/worker/src/generic.rs#L132)

## 一笔调用的接入方式

### 1. 以已验证的原生能力作为起点

本轮已用日常同摘要的 Runtime 实测。Ask 确实提供 session、always，选择任一项后同一会话重复查询均免确认。动态服务器在正常重开后两种选择都会重新询问，原生配置中没有该工具的持久覆盖。Full 的三次本地查询均无审批弹窗。这确立了会话记忆和 Full 的原生复用依据。接入产品 Worker 时使用独立 Home、两个普通本地 MCP 工具及回环模型响应，补验下述跨层边界。[实测结果和用例](24-connector-execution-audit-2026-11-22.md#固定-runtime-的三个原生对照)

- 对原生调用前审批，先解决受管工具的可写配置归属，再验证另一安装隔离和真正的跨重启命中。原生 `Auto` 工具策略才会生成记忆键；`Prompt` 强制询问但会规整掉记忆选项。两者与聊天权限模式里的「帮我批准」属于不同字段。
- 对现有 Gateway 服务端表单，分别验证人工、Guardian 和 full。Guardian 的服务端入口要求 `codex_request_type=approval_request`、`codex_approval_kind=mcp_tool_call`、真实工具名和空字段表单，工具参数采用已审阅对象。当前 Broker 元数据是封闭的双字段定位信息，扩展须先更新对应源契约。Full 复用原生对可自动接受空确认的判断；OAuth、凭据和真正需要用户填写的表单继续走各自流程。
- 证明一次用户操作只出现一张市场审批卡，并且 native 决定可以与 Worker 的同笔调用、原审批截止、owner 决定及实际发送对应。若既有调用前审批满足全部条件，直接使用原生路径，取消这笔调用的重复人工提示。仅展示两个菜单项或收到一次 `accept` 不构成资格。

**已经定位的差距。** 当前 `yijie_market` 的默认 `approve` 只消除了重复的调用前提示。服务器发来的普通表单和 Codex 自己生成的工具审批是不同入口；后者才调用原生保存函数。通用 server 收到的 `tools/call` 也没有 `codex_apps` 专用的原生 `call_id` 字段。不能把两次独立调用按工具名或到达时间拼接。[调用前审批实现](../../../../yijie-codex/codex-rs/core/src/mcp_tool_call.rs#L1203) · [自定义服务器的记忆键](../../../../yijie-codex/codex-rs/core/src/mcp_tool_call.rs#L1397) · [实际请求元数据](../../../../yijie-codex/codex-rs/core/src/mcp_tool_call.rs#L1083)

### 2. 用现有 Gateway 登记点保住精确身份与期限

以 **先登记真实调用，再由原生作决定** 为可落地的接线路径。在第一步已证明可直接复用的部分直接使用现有接口。对于固定版本无法从公开接口传递的身份或记忆效果，最小改动限于受管市场入口，把已验证的原生 MCP 请求交给同一套 Codex 选项生成、决定解析、记忆读写与配置重读函数。保留原始 `callRef`、独立截止和真实 responder。Desktop／Host 不建立记忆库、自动风险打分器或通用审批服务。

1. **冻结。** Native 按当前授权、任务忙闲状态及 `full_access_confirmed` 冻结有效模式、模型和连接器选集。Host 将已验证的有效模式随原 `prepare` 绑定给 Worker。旧提交只接受原冻结值，重新打开会话时逐轮准备。首次发送、已有会话、专家和多选入口使用同一规则。
2. **登记与资格。** Gateway 收到真实请求后复用 `register_call`，按 `callRef` 查回完整调用身份、工具、schema、参数摘要、作用域与原截止。将当前仅在人工回调中执行的专家真实方法／路由／单轮次数检查提到共用的调用准入位置。每种决定来源都经这一次校验。对于代理型工具还要绑定实际子方法及影响对象。
3. **取得原生决定。** Ask 把原生实际提供的可选范围传给 Desktop，并用原 responder 返回决定。Auto 走原生 Guardian，Full 使用原生对本次请求的确定结果。对于无人工回调的情形，Host 通过现有 Worker 私有通道读取本轮已登记调用，按需扩展有界的 pending 观察。观察本身只能读，不能创建调用。优先验证 rmcp 1.8 的 `RequestHandle.id`、原生 `targetItemId/reviewId` 与 Worker 记录的关联；传输请求 ID 须与活动进程、连接、线程、轮次及租约合用。当原生事件缺少唯一关联或保存结果时，只补在原生决定形成点产生的只读关联事实，再映射到现有通道。普通 `item/started`、任意 MCP 元数据和模型文字均不足以证明批准。[原生评审目标的生成位置](../../../../yijie-codex/codex-rs/core/src/session/mcp.rs#L702) · [Worker 私有通道](../../../../yijie-agent-host/internal/marketbroker/client.go#L168)
4. **双条件汇合。** 对同一个 `callRef`，Worker 等待实际原生接受和 owner 对该笔业务调用的许可。人工路径复用原决定；记忆命中使用原生规则命中事实；Auto 核对同一审核的结论；Full 核对本轮已确认的有效模式及业务准入，不产生虚构的人工批准 ID。两边任意先到都可等待，只有两边均满足才进入现有 `consume_execution`。拒绝、到期、撤销、正常取消优先。调用状态与单次消费在同一临界区核验，把等待放到锁外，保持续期和撤权通道畅通。
5. **发送与结果。** HTTP 边界逐次复核工具、参数、截止和取消条件。重复决定按原 operation / decision ID 查证，冲突和未知结果只读核对。原生已拒绝的调用不发送；人工接管后若 Codex 提出新的调用，它取得新的 `callRef` 和业务校验。已消费但缺失供应商结果时，在历史中显示结果待确认。

### 3. 把两个记忆选项真正落实

| 选项 | 生效范围 | 可验证结果 |
| --- | --- | --- |
| 允许一次 | 当前 `callRef`、当前参数摘要和原截止 | 下一笔调用重新作决定 |
| 本会话允许此工具 | 当前原生会话、同一用户／租户、已授权安装和同一具体工具／业务操作范围 | 同一会话后续匹配调用免重复点击；新会话无此记忆。会话重建时按原生实际寿命处理，界面标明范围 |
| 始终允许此工具 | 同一授权主体、连接账号、安装代际、已审工具及策略范围的原生持久规则 | 正常退出再打开仍可命中；更换账号、安装或工具定义时重新询问；用户可在对应连接器查看并撤销 |

工具记忆描述的是可重复使用的授权范围。每次真实调用仍使用新的参数摘要并校验账号、目标和策略。新日期可属于同一已批准查询，另一个账号、店铺、写入子方法或更高风险不继承。短期的 `callRef`、轮次租约、过期时间、凭据和原始参数均不作为长期键。授权失效期间禁止使用，重新授权时须核验实际主体和安装身份。

原生实现当前以 server、可选 connector ID、tool name 构造记忆键；市场通用工具名目前仅由 service 和上游名称导出。实施时优先使用现有原生作用域／工具映射承载具体安装身份。若无法区分两次安装，在构造原生审批键和读取该键的配置时绑定来自可信安装记录的非秘密标识和 schema／策略版本，实际业务工具名保持可对应。会话记忆继续进原生 ApprovalStore，长期记忆继续由原生 ConfigEdits 写入。Host 启动校验只认可经审的精确工具策略字段，保留对 URL、命令、环境和其他配置的原有约束。[原生键与持久选择](../../../../yijie-codex/codex-rs/core/src/mcp_tool_call.rs#L1397) · [配置写入位置](../../../../yijie-codex/codex-rs/core/src/mcp_tool_call.rs#L2099) · [当前配置层边界](../../../../yijie-agent-host/internal/codex/native_config_layers.go#L39)

具体到长期授权，先检查真实 user／project／plugin 配置层能否合法拥有这个工具覆盖。当前轮次临时注入的 URL 和 capabilityRef 应仅在该轮有效。对没有稳定配置父项的市场代理，优先使用原生已支持的合法配置归属；若仍不能表达安装隔离，则在原生 ConfigEdits 读写路径上仅补受管工具策略的作用域适配。不能将整个动态 server 配置落盘，也不能放宽 Host 对其他 MCP 端点的配置校验。两次正常冷启动间回读相同作用域的规则，才可交付「始终允许」。

落盘失败时，现有 Codex 可能退回会话记忆。UI 必须回读真实生效结果，分别显示「已记住」「仅本会话有效」或「未保存」。撤销通过原生配置编辑和活动会话缓存失效完成，同时阻止尚未消费的旧授权。重新打开历史只展示已发生的决定。SQLCipher 决定事实表、Host bbolt 和浏览器存储均不承担原生授权记忆。

## 续期、错误与兼容

- **轮次不续单笔。** `renew_market_scope` 继续限定在同一授权 revision、身份、进程和健康安装。原生等人、等 Guardian、命中长期规则、重连或收到迟到决定，都不能延长已登记调用的审批／执行截止。短证明收紧时，在实际发送前再次检查取消。具备双截止的网页工具保留原 HTTP 预算。
- **错误按影响范围显示。** 工具被拒绝或单笔审批到期只结束本次调用。真正的轮次租约到期／撤销仍由 Gateway 在可证明尚未发送时发出 0031 的闭合标记。晚到的决定或观察记录不得重新开放本轮市场工具。业务结果未知单独展示。
- **状态与可访问性。** 当前模式从 Native 确认后显示。审批卡在载入、提交和断连期间禁用动作；读回权威状态后恢复。Enter 允许一次，Esc 关闭下拉或沿用既有拒绝逻辑。保留拒绝、取消、键盘焦点、亮暗主题和最小窗口布局。菜单只展示本笔提供的范围。只读历史没有操作入口。
- **权限与隐私。** 安装、是否启用、授权账号、逐轮选集、工具风险和强制业务审批各按现有权威核验。模型和审核器只接收完成该决定所需的可审阅字段。无法安全呈现时转入已有人工审批或拒绝。产品审计保存来源、范围、脱敏引用、结果和时间，凭据由 Worker 管理。

本方案是文档，`contract-impact = none`；**拟实施的联动变更按 breaking 规划**。Broker 的 `Decision`、确认元数据与回执有封闭结构，老组件也明确拒绝 auto/full。先在 ADR-0021 追加三模式的本地候选设计，保留旧验收记录。Codex 原生协议／schema 以固定 Runtime 为权威；确需增加原生投影时先产生该处的真实定义，再由 Contracts 同步。易界私有 wire 先改 Contracts 的 broker-control、market-host v1/v2 和 Native IPC 源，继而生成并固定消费者引用。保持「本次结果」「是谁决定」「实际记忆范围」三个概念独立；既有字段继续表示原有语义。

新能力按整套配对启用。旧 UI 或任一旧组件配对时继续提供已有 ask/一次链路，对新模式明确提示版本条件并保留草稿；不得默改选定模式或去掉选集。部署顺序为兼容 reader、原生／Worker 能力、Host 与 Native、最后 UI。回滚关闭新 writer 与选项，停止旧活动租约，保留能读新历史和原生配置的 reader。新增记录不反向生成批准，不恢复已消费操作。[相关契约源](../../../../yijie-contracts/compatibility/market-broker-control/wire.schema.json#L1055) · [Host 审批源](../../../../yijie-contracts/compatibility/market-host-v2/wire.schema.json#L417)

## 开发顺序与验收

1. **原生能力实测。** 用上文三组对照锁定哪些路径可直接复用。产出实际调用／审核 ID 配对、原生提供的选项和持久化回读结果。欠缺唯一关联、作用域隔离或存储确认的路径进入最小原生适配，不以 UI 模拟结果代替。
2. **贯通一条查询。** 先以两个正常本地服务中的同名查询工具验证，沿原生→契约→Worker／Host→Native／Vue 顺序接线。启用真实决定后才按能力替换现有五处 ask 限制。首轮、续轮、专家路由都复用同一准入校验。
3. **完成记忆、撤销和历史。** 在同一连接器管理入口补齐查看／撤销；确认跨重开配置加载，验证保留旧记录、不同权限来源和执行结果的区分。随后在同一个固定开发入口对两种可选模型和代表性连接器复核。
4. **按下表逐项验收。** 用正常本地 MCP 和回环模型观察供应商侧调用次数。真实 Sorftime 仅在使用范围及调用额度明确时补一次已授权只读查询，并单独记录其结果。功能验收与供应商数据覆盖分别说明。

| 验收场景 | 通过条件 |
| --- | --- |
| Ask 的三种允许范围 | 同一工具连续调用，允许一次需再询问；本会话允许跨轮生效，新会话重新询问；始终允许经正常重开后生效。每笔业务调用的许可最多消费一次 |
