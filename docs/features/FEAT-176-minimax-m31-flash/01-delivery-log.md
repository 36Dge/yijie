# FEAT-176 · 工程实施方案

采用现有 Desktop → Tauri Native → Agent Host → Codex app-server → MiniMax Responses 链路。对本机同时交付的组件就地更新活动 v2 模型契约，生成同一批消费者，整套启用。文档阶段的契约影响为 `none`。实施按 `breaking` 登记，因为目录默认值、profile 封闭枚举、精确条数和序列化出去的模型身份都会改变。用户已于 2026-11-24 明确采用未公开产品的一次升级方式，历史兼容工程不在范围内。

## 2. 凭据、服务地址与实际请求

- **凭据流向。** 启动器沿用 `YIJIE_MODEL_PROVIDER=minimax` 和 M3 原密钥文件。Host 的 `loadMiniMaxAPIKey` 支持 `YIJIE_MINIMAX_API_KEY` 或 `YIJIE_MINIMAX_API_KEY_FILE` 单一来源，校验后仅把值作为 `MINIMAX_API_KEY` 注入受管 Runtime。两个模型引用同一个 `[model_providers.minimax]`。Shell、MCP worker、渲染器、数据库及诊断均沿既有隔离。更新凭据后按正常流程重启，两条模型路由都读取新值。 [启动器](../../../../yijie-desktop/scripts/run-local-demo-fast.sh) · [Native sidecar](../../../../yijie-desktop/src-tauri/src/chat/sidecar.rs) · [Host 读取](../../../../yijie-agent-host/internal/app/app.go) · [Runtime 环境](../../../../yijie-agent-host/internal/codex/runtime.go)
- **地址选择。** 当前 M3 使用 `https://api.minimaxi.com/v1`，用户提供的官网示例使用 `https://api.minimax.cn/v1`。首选在原受管 origin 上验证 Flash，沿用 Bearer、`wire_api=responses`、SSE 和已有重试策略。每次请求只使用一个受管 origin。正式验收分别记录目标 host/path、HTTP 结果与供应商响应模型。遇到鉴权或网络失败保留原结果，不以自动换域、换模型或重发来判断资格。若现用域名或账户无法调用 Flash，先区分地址、鉴权和模型资格。如需改用官网域名，共享端点的变更须同时验证 M3 与 Flash。 [当前 provider 常量与配置](../../../../yijie-agent-host/internal/codex/provider.go) · [官方 Responses 参考](https://platform.minimax.cn/docs/api-reference/responses-create)
- **请求字段。** 下方是普通回合的最小观测样例。实际 `input`、`tools`、`include` 和指令由 Runtime 构造。Flash 始终推理，省略 effort 会选 `max`，`none` 会被拒绝。Flash 请求省略 `service_tier`。原生 `model_reasoning_effort` 是线程配置，`turn/start.effort` 是回合参数，最终 HTTP 请求必须在 `reasoning.effort` 看到 `xhigh`。Chat 的顶层 `reasoning_effort` 和 Anthropic 的 `output_config.effort` 不用于此路由。 [模型与各协议对照](https://platform.minimax.cn/docs/guides/text-generation#chat) · [Responses 参数](https://platform.minimax.cn/docs/api-reference/responses-create)

```json
{
  "model": "MiniMax-M3.1-Flash",
  "input": "用一句话回答这个问题。",
  "reasoning": { "effort": "xhigh" },
  "stream": true
}
```

- **多轮与限额。** Responses 的 `previous_response_id` 和 `store` 不能承担会话恢复。沿用原生 thread、输入历史及 `function_call` / `function_call_output` 的 `call_id` 配对。推理 token 计入输出上限。`incomplete` 且缺最终正文时进入未完成状态。只按供应商返回的输入、缓存、输出、推理用量和既有原生事实记账。 [Responses 输入、输出和用量](https://platform.minimax.cn/docs/api-reference/responses-create)

**面向用户的错误归因。** 启动预检缺 Key 能直接提示配置问题。`/readyz` 未就绪时提示本地服务状态。供应商拒绝只在有可信错误码时细分为凭据、模型资格、限流或额度，否则给出通用失败及请求标识。Host 自身的 401 只代表本地请求鉴权。按当前操作的受理状态决定保留草稿或显示失败轮次，查询原操作不会改发另一模型。[Host 鉴权与错误应答](../../../../yijie-agent-host/internal/app/app.go) · [原生错误投影](../../../../yijie-agent-host/internal/session/service.go)

### 仅有 MiniMax 模型凭据时的正常启动

`pnpm client:dev` 的 Python 入口先准备 workflow，随后 Shell 在开发模式下还会执行 `builtin-web-session.py ensure`。冷启动网页执行器时，Infra 的 `configuration()` 要求存在服务端 Kimi Key，默认路径恰好与聊天用 Kimi 文件相同。Shell 还会预填聊天用 Kimi 文件路径。已在运行的网页服务可能掩盖这个依赖。桌面启动器冷启动走 `start`，接管已打开的客户端走 `services-start`，独立 `ready` 也会检查网页服务。[本机客户端入口](../../../../yijie-desktop/scripts/development-client.py) · [易界.app 入口](../../../../yijie-desktop/scripts/development-entry.swift) · [开发 Shell](../../../../yijie-desktop/scripts/run-local-demo-fast.sh) · [网页服务控制器](../../../../yijie-infra/scripts/builtin-web-session.py)

实施时由 Infra 的现有网页服务控制器对启动器报告可选服务是否已配置，区分“未配置”和“已配置但未就绪”。它只返回状态。Desktop 对 `start`、`services-start`、`ready` 及 Shell 的再次检查使用同一结果。仅有 MiniMax 模型 Key 时只启动聊天所需服务，经现有 `YIJIE_BUILTIN_WEB_ENABLED=false` 关闭 Kimi 网页 MCP，并省略其 Native 委派文件及未配置的聊天 Kimi 路径。已配置服务端检索时沿原受管凭据启动，Kimi 聊天的启停独立判断。若网页服务配置异常，其诊断保留，工具保持不可用。普通 Flash 依据自己的凭据和 Runtime 就绪状态发送，原生 `web_search` 仍按会话策略使用。[Native 网页装配](../../../../yijie-desktop/src-tauri/src/builtin_web.rs) · [Host 网页策略](../../../../yijie-agent-host/internal/codex/builtin_web.go) · [Kimi 模型凭据读取](../../../../yijie-agent-host/internal/app/chat_model_config.go)

## 4. 实施顺序与启用

1. **冻结本版定义。** 从当前活动契约生成默认常量、模型定义与调用方类型。现有生成器校验 `x-model-profiles` 首项等于 `default_profile.const`，并将全部 profile 与活动枚举逐项比对。同步更新当前固定的 family 版本、依赖投影和 source locks，登记本次有意的 breaking 差异。产品采用当前本机组件同批更新。[模型生成器](../../../../yijie-contracts/scripts/generate-chat-models-v2.mjs) · [多入口投影同步](../../../../yijie-contracts/scripts/sync-model-call-surfaces-v2.mjs)
