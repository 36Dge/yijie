# 杭州天气托管搜索收尾回归

2026-11-24，日常客户端 11:54 的一轮杭州天气问答记录了 5 个 Kimi 托管搜索 ID，模型开场一次，随后四次发出同一句进度。第二、三次查询词完全相同。两次同参 Pro 请求共用一个服务端操作，取页次数为零。这一轮在 11:55:33 正常完成。

本文记录首次收束托管搜索时的计数。停滞分支后来修复了额外的进度播报，最新回归同时核对了实时事件、落盘记录和重读历史。[后续原始播报回归](46-hangzhou-repeated-progress.md)

## 修复范围

`contract-impact = semantic`。易界普通聊天沿用原生 Runtime 的步骤、权限与收尾流程。Kimi 在一次模型请求内部执行托管搜索，本地收到完成事件时该次搜索已经发生。修复控制后续请求声明的工具，也指导模型在当次搜索已经满足问题时直接交付。[Kimi Responses API](https://platform.kimi.com/docs/api/responses)

- 第一次搜索返回后，下一次采样可以依据已取得的材料直接回答，可以读取已知来源，也可以调用本地函数 `request_followup_search` 写出缺失事实和针对该事实的查询。该函数本身没有网络请求。
- 一次被接纳的补查只让下一次采样使用原本可用的托管搜索。模型可以为不同事实继续研究。已尝试的查询、同一缺项的重复请求，以及空状态查询均有对应处理。同一缺项确需另查来源时，可以指明新的站点。
- 同批其他工作返回材料时先重新评估。运行中的独立工作和新的用户输入沿用原有优先级。普通进度和搜索事件按真实执行保留，计数读取原生历史。
- 变更由固定上游上的 0036 补丁及相应的本地版本校验承载。回退使用上一套匹配的 Runtime、Host、桌面来源记录，经过正常退出与固定入口构建后生效。

## 验证方法

取 11:54 这一轮的公开模型消息、托管搜索调用和工具回执。旧版对照重放原步骤。新版重放相同的开场、第一项托管搜索、原进度和空目标查询，之后本机测试服务根据 Runtime 实际声明的工具和已交付的材料响应。记录中 Pro 的默认摘要只给了部分日期。可读回归材料另外取自同一日、同一发布时刻的中国天气网原页，保留来源、页面摘要和七行天气。脚本只在工具真正返回后读取这些行。缺项分支只扣去最后一天。停滞分支重放原模型的重复播报和空查询。回放中的模型应答由本机脚本提供。[固定预报材料](references/hangzhou-hosted-source-20261124.json) · [杭州预报来源](https://www.weather.com.cn/weather/101210101.shtml)

每个受测版本均通过真实 Host 启动独立 Runtime 与普通对话。回归将服务端完成的搜索 ID、原始进度与最终正文摘要，逐一与 `thread/read` 的同轮条目比对。重复播报次数按每段完全相同文字从第二次起计数，总进度数包含开场。另获授权的一轮自然问答使用原中文问题、真实 Kimi 和托管搜索。在本机接收请求后先预占额度，遇到结果不明就停止继续发送。[回归入口](references/check-hangzhou-hosted.py) · [原生历史核对](../../../../yijie-agent-host/internal/codex/hosted_search_followup_integration_test.go)
