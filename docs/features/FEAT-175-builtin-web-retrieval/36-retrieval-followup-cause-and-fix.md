## 追加检索是否必要

| --- | --- |
| 首次 Pro | 接受的研究规则要求 Pro；但 10 条结果中 8 条 URL 指向 3.15，单靠这份结果不足以完成 3.14 对比 |

| PEP 750 定向 Pro | 合理补充：新增了模型可见的模板字符串机制正文。若只列变化名称，Summary 已足够；若说明变化并给具体证据，这次补查有依据 |
| PEP 734 定向 Pro | 对这份三点短答可省：首个 Fetch 已包含新模块、原来仅 C API 可用及多核并行的正文证据 |
| 两次 PEP 779 Pro 尝试及发布页 Fetch | 超出已选三项变化的必要证据范围。前一次 Pro 是 busy 拒绝，后一次是模型另发的新查询，不是底层 HTTP 自动重试；发布页也不是完成这三点短答所必需 |

没有据这一中断样本进一步堆叠提示词，也没有把没有最终答案等同于模型必然无法完成。第 34 页共享研究规则、三个工具描述和第 35 页评分／费用保持原样。

## 繁忙拒绝：已定位并修复容量衔接

第二组同时发出三项 Pro，前两项在服务端仍处于活动状态，第三项返回 `busy` 且没有对应 operation。API 的 `Repository::Admit` 在活动数达到 2 时拒绝；MCP 网关原先没有与之对应的发送容量约束。

固定 Runtime 的 `McpHandler::supports_parallel_tool_calls` 对只读工具允许并发，既有独立函数适配原样保留这一能力。其当前 MCP 配置提供的是是否支持并发的布尔值，没有每个 MCP 服务的数值并发上限。保持真实 `readOnlyHint`、原生 auto、发现、工具选择及取消机制，在服务适配边界补齐容量衔接即可，不需要修改 Runtime 或添加 Host 调度器。

最小实现为原 `WebGateway` 中的共享 Tokio semaphore：

- 同一网关最多同时派发 2 项应用检索，与现有 API 限额一致；其他工具命名空间不受影响。
- 先通过原 Host 准入解析根线程／轮次并绑定已有取消 token，再等待容量。因此排队中的子调用也受原根撤销和 binding clear 控制。
- 新的同源 `gateway_queue_wait_seconds=5` 限定等待；到期返回既有 `busy`，等待中取消返回既有 `cancelled`，都发生在 API operation 创建／供应商派发之前。获得容量后再次检查取消及原准入期限。
- 成功或失败后用 RAII 释放槽位；原操作、HTTP、取消与 401 未派发证明下的既有处理保持，不对 busy 或未知结果重试。

原生 MCP 60 秒、Host 准入 5 秒、API 45 秒与新增等待 5 秒在主执行路径上留有余量。生成时校验此关系。这个修复缓冲同一客户端的短并发突发，不承诺消除其他客户端压力或持续满载产生的真实 busy，也不代替服务端权限与配额。

## Fetch 超时：定位边界与诊断接线修复

历史失败 operation 的数据库时间为：创建 `06:45:35.758839Z`、期限 `06:46:20.758Z`、结束 `06:45:48.109159Z`，实际约 **12.350 秒**。原生停止发生在 `06:45:54.494Z`，晚于错误返回。

当前错误传播链与时间共同指向供应商 HTTP 超时响应：默认 Fetch 本机请求预算是 15 秒，API／executor 外层为 45 秒；网关自身请求失败会返回未知结果，而已观察到的是 worker 归一化后的 `timeout`。adapter 将上游 HTTP 408／504 映射为该错误。**这是依据时间和源码排除外层路径后的推断，旧记录没有保存具体 HTTP 状态，不能确证究竟是 408、504，或供应商内部为何抓取失败。** 不能据此声称延长本机总超时已经能够解决。

已确认的诊断缺口是双重的：服务端 Rust executor 调用 adapter 时传 `Diagnostic::default()`，已有的 HTTP 状态观察没有输出；Go owner 又把 worker stderr 丢弃。现已复用原 `Diagnostic` 机制接通服务端私有记录：

1. Rust 服务执行使用同一份枚举／数字诊断写入 stderr；上游 HTTP 状态继续记录为 `response + httpStatus`，本机计时到期明确记录为 `expired + null`，传输不可用单列。
2. Go owner 只接收允许的 web 阶段及事件、数字时间和 HTTP 状态，并用自己已验证的 operation UUID 关联后写入既有服务日志。输入行最多 512 字节、每操作最多 8 条；其他日志不原样转发。
3. 查询词、URL、正文、原始异常、header 和凭据不进入这份记录，也不进入模型结果或 App 公共事件。原文件式 provider 诊断仍走原路径与原上限。

Fetch 输入仍只有 URL；15 秒预算、HTTP 408／504 到既有错误的映射、不重试及 `unknown / may_have_dispatched` 的保守结算语义均未改变。新诊断可让后续实际错误直接区分来源，不能补造这次已丢失的状态。
