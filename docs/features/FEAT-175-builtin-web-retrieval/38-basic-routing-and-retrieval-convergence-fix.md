# FEAT-175：Basic 自然选路与追加检索的定位、修复

2026-11-16。本轮已完成最小产品修复、定向本机验证和正常开发客户端构建。新增真实模型／付费搜索调用为 **0**，没有公开分发、提交或推送。真实模型的自然选路、检索收敛和长度遵循尚未复验；第 37 页的失败及费用记录保留，FEAT-175 仍为 implementing。

## 根因与证据边界

### 1. Basic 已有成功执行证据，选路指导存在冲突和投影缺口

- 第 37 页 C01：MiniMax 收到“采集三条 asyncio 入门资料，只列标题、网址和一句摘要，供之后挑选阅读”，产生 11 次原生搜索、0 次 Basic，还调用了一次无关的 `echo probe`。
- 实际会话的 Host developer 指令仍写着未选适用连接器时 `Otherwise use exposed native web retrieval`。这与内置工具无需选择连接器的产品设计不一致。C01／C03／C06 的该指令片段相同，SHA-256 为 `9e25025d3b87686f68b5518b6d36635fb5234971ae1c89c9fde555736a0e193d`。
- 固定 Runtime 的 MiniMax 配置将 MCP 命名空间展开为独立函数，保留函数描述、丢弃命名空间描述。此前仅 Pro 补齐了公共研究规则；Basic 的独立描述没有带上命名空间的免选集及完成规则，也没有明确说明资料列表与普通问答的边界、云端预搜索不能替代 Basic 采集步骤。
- C06 明确指定 Basic 后，只调用一次即返回三条资料，原生搜索为 0。这证明 C06 的执行器及结果链路可用，不能反推 C01 首轮工具必然可见，更不能据此宣称只有模型问题。

App 的正常启动会等待首次资格申请／安装，再交出 Host bridge；首次申请最多等待 5 秒，失败时保留原生搜索并暂不暴露内置 MCP。C01 没有保存首个供应商请求的工具表，因此不能排除当时的暂时可用性问题。本轮复用现有固定 Runtime 用例，验证成功安装后、无连接器选集的首轮 MiniMax 确实得到三个工具及新规则；没有为无法证实的历史假设新增重试或启动门禁。

### 2. 过度检索主要发生在把交付范围扩大为额外核验

| 旧样本 | 已观察行为 | 判断 |
| --- | --- | --- |
| C04 Kimi 资料列表 | Basic 返回 8 条元数据后，又有 Pro 3、Fetch 2、原生搜索 5；最后三条链接来自后续结果 | 列表任务被扩展为正文读取与链接核验。足够相关的标题、URL、摘要本可支撑列表；不能声称最终列表只由第一次 Basic 完成 |
| C03 MiniMax 研究 | 首次 Pro 及送入模型的 Fetch 前段已有注解／多解释器证据；模板字符串机制正文未完整进入该前段 | 定向补查 PEP 750 有依据，不应一概禁止追加查询 |
| C03 后续检索 | 又搜索发布日期、发布公告及额外博客印证 | 超出“三项变化、正文片段、300 字”的交付范围，增加调用和最终篇幅 |
| C02 指定 URL | 原 URL 和仅增加锚点的 URL 返回完全相同正文 | 换锚点不是 Fetch 分页。两次正文 SHA-256 同为 `549d3ad633fa9a8b56ee4675695e17c62e173b8cb0913118d5e799d19e722846` |

Host 原有“优先原始官方来源／搜索命中不能证明具体主张”的通用规则没有区分“介绍供之后阅读的资料”与“验证正文结论”；笼统的“证据足够就回答”也未说明必须先完成任务所需的 Basic／Pro 步骤。C02／C03 还把短摘要之后的表格、引文、说明当作额外空间，导致全文超长。

`echo probe` 已被原有规则明确禁止。本轮保留该规则并记录违规，不以新增执行调度器或更多无关命令处理模型的不遵循。以上证据能确认产品指导缺口，不能观测或量化模型内部每一项决策成因。

## 最小产品修复

`contract-impact = semantic`；原整项 breaking 分类保持。权威源是 Contracts 的 `compatibility/builtin-web-retrieval/policy.json` 及 Host 原有指令适配，仍为未发布 0.1.0 本地候选。

| 交付意图 | 当前规则 |
| --- | --- |
| 普通问答 | 默认原生 `web_search` |
| 无站点／日期限制的资料列表、素材采集 | Basic；元数据列表使用 `include_content=false`，在 schema 允许范围按所需条数设置 `limit`；需要收集正文时才设 true |
| 研究结论、需要正文证据的比较，或显式站点／日期过滤 | Pro；实际传入 `sites`／`time_window`，复用同一需求已经足够的 Pro 证据 |
| 明确读取 URL | Fetch；列表里出现 URL 不等于要求逐页阅读 |

实现只调整已有规则及其投影：

1. 在 Contracts 单一来源增加 `collection_instructions` 和 `completion_instructions`。现有 generator 把完成规则投影到三个独立函数，把 Basic／Pro 的任务规则分别投影到相应函数，并组装命名空间说明。无需新增工具或调度接口。
2. 资料列表明确以足够相关的标题、链接、摘要为完成条件，不因“核验这些链接”自动升级 Pro／Fetch；追加检索须填补用户交付物中的具体缺口。资料摘要不能冒充已读正文、正文引用或研究结论。
3. Fetch 明确成功截断是可用的部分证据；没有分页／可调正文上限，改锚点不构成索取缺失尾部。缺少必要事实可定向 Pro 或说明局限，用户明确刷新另算新需求。
4. Host 去掉“未选连接器只走原生搜索”的旧分支，依当前可用工具及描述选路，保留适用所选连接器的优先权。完成条件同时包括必要检索步骤与证据充分性；长度／格式约束适用于整个最终答复，包括表格和附注。

继续复用 Codex 原生 MCP、tool_search、Code Mode、独立函数投影、只读 auto 权限、正常续轮与取消。没有关键词分类器、Host planner、调用次数计数器、自定义收尾循环、URL 缓存或 Runtime 核心改动。没有调整原生搜索开关、专家政策、凭据／准入／额度、并发、超时或重试。

Basic／Pro／Fetch 的输入、输出及描述外工具字段逐项相同；四消费者经 canonical generator 同步。MiniMax 三个描述合计由 1,559 增至 3,157 字符，增加的文本用于补齐被独立函数路径丢失的规则；未把完整命名空间逐份复制。实际 token／费用收益不能用字符数或本机测试推算。

## 尚未完成

新构建尚未进行真实模型复验。后续只需沿用原始自然任务核验：MiniMax 首个应用检索是否自动 Basic；资料元数据足够后是否直接交付；研究是否仅为真实缺口追加查询并满足全文长度；指定 URL 是否复用同页正文。Kimi 的共同完成规则可用原资料列表任务作针对性对照。
