# FEAT-175 发布、兼容与回滚方案

本轮未发布。完整目标为其他用户 App 默认可用；本机通过只能记录为局部开发资格。

修订 2 增加硬前置：正常产品身份、网页委派与主模型服务必须分别有发布资格。托管 Kimi 搜索 Key 不会使当前要求模型配置的 ModelAvailable 自动通过；没有基础模型服务的新设备不能用直接 REST 调用替代完整聊天验收。

## 激活顺序

1. 用户接受技术方案与适用 ADR；形成源契约及精确 consumer pin。
2. 准备正常产品身份、秘密管理、TLS／服务身份、运营账户／额度和服务观测；完成适用身份安全基线，禁止把 local direct-entry 暴露公网。
3. 先部署 API／Connectors 的新入口和兼容版本，确认真实服务 ready；准备检查不得以收费搜索当无声 probe。
4. 下发支持新入口的 App，切换只发生在旧 turn 结束／正常取消后的新提交；旧数据继续读取。
5. 在没有开发者 Key／环境的新设备验证安装即有工具、双模型／专家正常使用、取消与重开；全部验收达标后再扩大分发。

## 回滚原则

- 新能力服务端／客户端具有受管停用开关，作用于新调用，不伪装成成功；普通聊天与不依赖它的原生搜索继续遵守原配置。
- 不自动回到用户 Kimi Key、不自动重建旧安装或选择、不用 shell 抓取补偿。
- 保留新 reader、新业务记录和旧市场历史，不降数据库格式或清理用户数据。
- 已发送／unknown 操作只核对既有事实，禁止回滚时重放；可取消等待不等于撤销供应商费用。
- 退出／换租户及服务撤权同时撤销旧检索委派；清理本机凭据不代替服务端授权检查。查重记录和支持窗口保留，旧 ID 过期不能被重新解释为新派发。
- 原正文无法恢复时显示 result_unavailable，不能用后台再抓取补偿已丢失结果。正常取消仅在执行端发送线性化点之前生效时保证零请求。
- 进程更新用应用正常退出和原构建入口；不能在运行中覆盖二进制或强杀制造重启。

## 上线前仍需明确

实际区域／域名、可用身份基线、运营 Key 管理、用户额度／资费、部署与签名制品、支持版本窗口和观察责任。用户已经选择托管与自动只读，但并未授权本轮购买资源、付费调用、提交、部署或发布。

零数据丢失、已提交历史可读和无隐式外部重发是回滚必验项目。无法证明回滚 reader 理解新历史时保留新 reader，只停用新调用能力。
