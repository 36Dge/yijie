# FEAT-175 后续实施依赖顺序

这是待审计划，不是执行授权。目标 Runtime 核心零变更；任何新增 Runtime 补丁必须重新给出缺口证据和方案。

## S1 — 原生可行性与权威契约

先核定既有 canonical 配置／MCP 类型，并形成新工具、公开 API、startup、必要审批／UI 投影的源契约候选；先生成再实现消费者。当前固定 Runtime 的早期可行性检查仅使用既有标准 schema 和普通本机 MCP／模型响应，不将临时 spike 当成已发布新协议。随后验证应用工具无需市场 selection、两模型组织、auto 只读执行、prompt 的薄接线、暂停计时及专家恢复；没有上游业务调用。新协议实现必须由 source-first 候选约束，不能先写 Host DTO 后补契约。

## S2 — 服务端能力与公开前置

落实已确认的服务端持钥；复用 API 产品身份、授权、审计和私有存储，补最小调用幂等／额度准入；Connectors 共享现有 Kimi adapter 的实际执行与归一化。禁止把运营 Key 下发客户端。公开身份、TLS、服务身份、部署和运营额度不就绪时，不宣称开箱分发已完成。

## S3 — 应用内置接线

Host 自动启动／共享 worker 并配置 yijie_web，不依赖市场总开关或非空选择；配置合并在市场服务器整理后添加 builtin，避免误被禁用。移除专家 blanket 搜索覆盖，标题／input-only 显式限制。将产品会话刷新与业务请求绑定到现有身份机制，供应商 Key 不进入客户端。

更新 canonical 工具描述，保留稳定 wire 名称与原生检索 guard；MiniMax namespace／Kimi deferred 发现沿已有模式。默认 auto，只读执行不要求额外市场审批；按需补标准原生确认投影。

## S4 — 展示、兼容与 eval

将既有 WebRetrievalResult 接到普通 native MCP 结果，完成新错误／来源显示；旧市场入口停止用于新请求，其他连接器和旧历史保持。修正实际引用旧操作前提的 Skill／文档，不批量改专家角色。完成普通／专家、双模型、恢复／取消与冻结路由评测。

## S5 — 受支持分发

按 [09](09-release-and-rollback.md) 先服务端后客户端。使用无开发者凭据的新设备做真实使用和重开；完成适用公开／生产门禁和三项 E2E 后，才可将需求标为已交付。签名、提交、推送、发布与真实调用预算分别授权，不从方案确认推导。

同一阻塞连续三次先复盘证据与假设，不机械重试。已存在的未提交代码不归入本需求；各仓实施前重新记录状态和来源。
