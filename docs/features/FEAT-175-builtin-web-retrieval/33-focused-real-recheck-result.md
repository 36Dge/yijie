## 已确认的原因与不能越过的证据边界

**1. 工具接入、执行与模型自动选路是三个不同问题。** R03 的实际成功说明 MiniMax 能通过当前独立函数路径调用内置 Fetch；R02 说明同一服务的 Pro 链路可用。R01 没有发起应用工具调用，因此没有观察到 Pro 的权限拒绝、参数错误或服务失败；不能把此次“未选 Pro”归因于这些执行错误，也不能推定 MiniMax 的 Pro 实际执行已被验证。

**2. 公共规则确实没有等价投影到两种模型表面。** 固定 Runtime 候选包含既有 `0020-native-tool-integration.patch`：`function_namespace::adapt` 从命名空间取出单个 function、改成扁平名称，保留函数自身描述，未合入 `spec.description`。Host 对 MiniMax 将 `mcp__yijie_web` 放入既有 `function_namespaces`。第 [31 页](31-routing-and-repeat-fetch-fix.md)的同制品原生协议验证已确认这些函数描述到达模型侧；R02/R04 实际发现结果则直接显示 Kimi 收到完整公共规则。

现有 `policy.json` 把“供应商预搜索不能替代用户要求的过滤及正文证据”只写进 `server_instructions`；Pro 自身描述虽然包含研究优先、`sites/time_window` 与正文证据，却没有这条衔接规则。上轮认为关键公共规则已在两种描述中完整保留，判断不充分。本次确认的是**产品规则投影缺口**，不是新发现的 MCP 不可用，也不是必须改 Runtime 的证据。

此外，`first applicable app retrieval` 只规定发生应用检索时的次序，并没有清晰规定：已得到足够 hosted 证据时，这类研究是否仍必须调用 Pro。R01 从原生检索得到足够资料后直接答复，与这个规则空隙相容；但不能从轨迹获知模型内部因果，不能宣称仅补一句话就必然解决选路。R01 按预先冻结的研究选路标准仍为失败，不事后降低标准。

**3. 两次 Fetch 都真实覆盖了截断分支。** 返回正文均为 16,993 字符，SHA-256 为 `d9bd231f4c52b7f1a252ae44de7e861e6fd3d14d9c81e50667ff0c24760d7b12`，与上批三次重复抓取的正文相同。所问 Summary 位于可用部分，两个模型都只执行一次并完成摘要。说明相同内容／`truncated=true` 并不必然导致重复，也没有看到传输层自动重试。

Kimi R04 主动只输出 `structuredContent`，避免了旧 P03 同时打印两份正文的情形；R02 第一次 Pro 仍打印完整包装，第二次才提取结构化片段。因此不能把“所有 Code Mode 结果已去重”写成已完成。

MiniMax R03 的模型上下文输出为 11,986 字符，含原生 `5658 chars truncated` 标记，除了服务端正文截断还发生了 Codex 的上下文裁剪。对应既有 `McpToolOutput::response_payload` → `truncate_function_output_payload`；Code Mode 则可取得原始 `CallToolResult`。两者都是当前正常路径，不是结果未送达或数组序列化失败的证据。此次 Summary 保持可用，不需要扩大输出上限或另造分页／重复抓取器。

**4. MiniMax 的“三次抓取”是未经证据支持的答复内容。** 原生轨迹只有一个 Fetch invocation，服务端只有一个对应 operation；本聊天已记录的非 assistant 输入里也没有这句话。应判为执行来源自述错误，不能倒过来把它计为三次调用。没有证据证明串会话、历史泄漏或真实重复执行，不能据此展开猜测式修补。

**5. 此轮不构成单因素因果实验。** 研究原文与旧 P03 相同，Kimi 这次实际选 Pro 是正向证据，但每模型只有一次。明确 Fetch 的任务比旧研究任务范围更窄，并直接点名工具；它证明受控结果消费，不证明自然自动选路，也不能单独证明提示修改是改善的唯一原因。缺失尾部确实需要其他证据、自然研究自行 Fetch、刷新、跨轮相同 URL 等情形没有在本轮验证。

## 下一步最小产品工作

优先处理已证实的**规则投影等价性**：在 Contracts 同源政策中明确本次研究／站点限制标准，并把对这种任务不可缺少的公共语义投影到 Pro 的独立函数描述；经原 generator、worker 和固定 Runtime 的既有工具说明入口消费。普通问答继续原生搜索，保留原生权限、发现和调度；不增加 Host 意图分类器、另一个调度器或强制关闭供应商预搜索。

这一步应只复用现有两模型原生协议用例核对有效描述，不新增通用框架。本轮没有实施这项后续变更。后续真实复验仅应针对 MiniMax 尚未通过的自然研究样本，另有适用费用授权后才执行；不机械重跑已通过 Fetch。如果规则已完整到达仍不遵循，应评估这个产品标准是否需要显式“研究”入口及既有原生工具策略，而不是无限叠加提示。MiniMax 的错误操作次数另记为答复真实性缺陷，不把它改写成执行层重试问题。
