## 第二个任务的原生顺序

按原始 `item/started` 顺序：

1. 原生搜索 Python 最新稳定版本；Runtime 随后原生发现工具。
2. 再次原生搜索；接着调用两个 Fetch，目标是 Python 官方发布页面与下载页面。
3. 第三次原生搜索；调用限定 `python.org` 的 Pro。
4. 再调用三个 Fetch，其中第一个准入，后两个返回本机 HTTP 429；随后 turn 以 failed 结束。

第五、六个 MCP Item 的错误明确来自本机 `FEAT-175 verification admission stopped`。此时本机 MCP 准入已达每任务 4 次，模型 HTTP 也已达该任务 4 次。计量器停止后未继续向供应商发出请求。5 个已发模型 HTTP 均成功，因此不能将本次 429 归为 Kimi 服务限流。

v1 计量器只保存了泛化的 `Admission or control rejected`，没有分别持久化各拒绝的封闭原因码与先后时间。根据原生 Item、准入数量及固定代码可确认本机配额拒绝；不能进一步伪造精确的并发拒绝顺序。原生错误里的 `exceeded retry limit` 是终态错误文案，不代表计量器实际进行了额外付费重试。

## 能确认的事实与不能外推的结论

Kimi 这两个任务的默认检索行为分别是“无需检索”和“原生搜索优先”。第二个任务的三个 query 均与 Python 稳定版本／官方发布信息相关，但没有交付最终版本号、日期和依据。因此首次选路符合预期，与整个任务失败同时成立；不将 route MATCH 解释成任务通过。

**两次原生搜索发生在第一次 MCP 返回之前。** 所以本轮的额外 hosted 不能全部归因于合成 MCP 材料。另一方面，后续工具明确返回合成内容，模型继续查证也可能由此产生；本轮无法估算真实产品重复检索率，不能证明后续所有补查都无必要。

官方来源要求下，模型从原生搜索转向 Fetch／Pro 本身也不充分证明选路错误。当前需求是普通问答默认原生，不能从单个失败样本直接推出“普通问答必须禁止所有独立工具”。需要分别判断首次动作、后续工具的理由、额外 hosted、完整回答与真实证据质量。

本轮实测确认 Kimi 的原生 `web_search` 实际发生，并验证了当前 profile 下的原生工具发现和调用。没有验证 MiniMax 的本轮真实能力，没有验证 Q2-03—06 的首次选择，也不覆盖专家产品接线、云端托管与新用户开箱可用。

原评分文件保持原样，其中 `live_execution_performed=false` 表示离线评分器本身没有发送真实请求；`evidence_kind=recorded-native` 和执行 ledger 明确记录了这次真实运行。该字段命名存在歧义，后续版本应拆清评分器行为与样本来源。

## 复审发现与下一步顺序

| 发现 | 影响 | 下一步处理 |
| --- | --- | --- |
| Q2 驱动要求完整 turn 成功，但独立工具返回明确合成材料 | 时效事实任务可能持续补查，先耗尽配额，阻断剩余首次选路样本 | 零费用设计 Q2-v2，将“首次动作／参数采集”和“完整任务／证据质量”分开；首次动作采集结束采用原生中断，不能把 interrupted 冒充完整回答通过 |
| 原生搜索在 MCP 返回之前已经重复发生 | 仅调整合成结果无法解释或消除全部额外 hosted | 单独记录每次 provider 请求与原生搜索的对应；以原生配置／接口证据研究，禁止偷偷删工具或改输出上限制造通过 |
| 本机拒绝原因过于笼统 | 并发 MCP／模型拒绝的精确诊断受限 | 在新的 QA 版本增加封闭原因码、准入面、任务／轮次及计数，不记录凭据或任意异常正文 |
