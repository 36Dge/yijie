# 同轮重复取页与进度消息修复方案

2026-11-24 · FEAT-175 · 本文保留修复前的设计基线。实现中修正了 Code Mode 的结果传递和 Kimi 的最终作答上下文，见[复审与杭州实测](44-hangzhou-fetch-regression.md)。

杭州天气现场只有一次用户提交。Kimi 四次输出相同的进度文字，四次请求读取同一网址。第一次取页已返回 11 月 23 至 29 日的逐日预报，后续三份正文与首份完全一致。API 记录了四个独立完成的操作。直到桌面发出中断，这一轮仍在续行。

修复目标是让一次成功取页支撑后续作答。即使模型再次提出同样的请求，对外取页至多派发一次，重复进度在默认阅读视图中只占一条，持续索取相同材料的执行有明确终态。供应商在模型请求内执行的托管搜索单独计数。

## 1. 由 API 保证同轮同页至多派发一次

将 Fetch 接入 Pro 已有的轮次准入、原子派发和只读结果查询。Host 核验绑定、根轮次和实际调用方轮次后签发作用范围。API 复核当前授权，在数据库事务内按绑定、授权版本、轮次范围、工具和有效参数摘要确定原操作。并发、调用 ID 变化和网关重连均通过同一条唯一约束裁决。网址沿用 Fetch 的 HTTP 语义，保留路径大小写、查询参数及其顺序，只移除约定不影响取页的片段。新用户轮次可以读取最新页面。轮内明确要求刷新时，新的读取范围须来自真实用户输入。

| 已知状态 | 当次调用的处理 |
|---|---|
| 首次请求 | 分配原操作，取得派发权，调用供应商。 |
| 原操作在途 | 关联原操作并等待。每个调用保有自己的 ID、回执和等待取消语义。 |
| 原操作完成 | 只读取得同一份 Fetch 结果。保留网址、正文和截断状态，Code Mode 可以继续读取其中某个段落。 |
| 正文已过期、已逐出，或派发结果未知 | 保留原操作引用，返回真实的可用性或未知状态，新增派发为零。只有确证未派发且原因可恢复的操作才进入既有重试规则。 |

给 Fetch 定义可协商的操作回执，表达本次调用、原操作、首次／合并等待／复用、派发状态、正文可用性和材料摘要。原 MCP 结果继续按 Fetch schema 校验，可信回执走工具元数据。服务端持续保存操作归属和摘要，正文沿用已有的有界保留机制。数据库现有约束只接纳 Pro，实施时需要新的 expand migration 和匹配的 API 读写路径。恢复中的调用若不能证明原范围和派发状态，保守地返回不可恢复状态。[现有数据库约束](../../../../yijie-api/internal/platform/migrations/sql/00007_scoped_deep_search.sql) · [网关准入与复用](../../../../yijie-connectors/worker/src/builtin_web_gateway.rs) · [轮次归属](../../../../yijie-agent-host/internal/session/deep_search_receipt.go)

## 2. 由 Runtime 根据实际交付的材料决定续行

扩展现有 `search_progress` 和 `answer_completion`。在内层工具完成时取得可信回执，在外层调用返回时核对该步实际交给模型的材料。比较原操作、结果版本以及可见内容，忽略调用 ID、耗时和重复包装。同页首次输出另一段正文算新材料。首次调用只取到数据、脚本尚未把正文交给模型时，应允许后续取用。无法确认两次输出等价时，继续接受该步的实际工作。

| 模型步骤 | 拟定决策 |
|---|---|
| 首次取得材料，或有独立工作取得进展 | 写入本轮上下文，允许正常作答、补查或交付产物。并行批次内多次等待同一个操作只算一个模型步骤。 |
| 后续一步再次索取已交付的同一材料，只有重复进度或无变化的状态查询伴随 | 复用原操作，发一次纠偏，指明已有来源和材料，允许模型直接作答或指出并补查具体缺口。 |
| 纠偏后仍只索取旧材料、复述进度或查询同一空状态 | 用户没有追加输入，且独立工具、审批、子任务均已结束时，进入现有只作答流程。该阶段发给模型的工具集为空，包括托管搜索，执行入口也拒绝新的工具派发。沿用最多两次补答，输出有来源的答案或明确的部分结果。仍只有进度、没有交付时按既有失败终态结束。 |
| 出现新来源正文、首次输出的片段、独立任务结果，或新的用户要求 | 继续相应工作。已完成页面的派发保护仍有效。用户中断优先，直接结束。 |

把当前“出现任何托管搜索便跳过纠偏”的判断拆开。新搜索 ID、关键词微调、仅多出候选链接或 `get_goal` 再次返回空值，都不能单独清除已确认的重复取页。模型开始使用另一来源、返回用户要求的来源清单或交付新的材料时，承认这些进展。纠偏状态跨中间的无效步骤保留，避免两次重复之间夹一次空查询就重新开始计数。运行中的独立工作可继续完成，关闭一个重复读取不应提前结束整项研究。[现有检索纠偏](../../../../yijie-codex/.yijie/patches/chat-models/0027-scoped-search-progress.patch) · [原生补答上限与工具过滤](../../../../yijie-codex/.yijie/patches/chat-models/0013-answer-completion.patch)

进入只作答流程时，应让模型仍能读取已有证据和来源。若上下文压缩已移走正文，按原操作只读取回所需片段。连续取得相同的“结果不可用”也属于无新增材料，此时补答应写明缺口。

## 3. 桌面折叠相同进度，保留真实活动

在时间线的阅读投影中，同一调用方、同一用户输入段内，经确认的纯文本 `commentary` 按完整正文比较，只统一换行和首尾空白。保留第一条的位置，后续完全相同的正文折叠进过程详情。温度、日期、链接或结论发生变化均展示。最终答案、错误、打断、审批和附件保留各自的呈现。取页活动按可信原操作引用汇总，每个逻辑调用仍可追溯。供应商托管搜索按原生事件展示。

流式预览仍以原消息 ID 更新。对于进度或阶段尚待确定的预览，仅在新文本仍是既有进度正文的前缀时暂缓显示第二个正文块。首个不同字符到达便显示完整缓冲并继续流式输出。只有最终确认属于进度且全文相同才折叠。一旦确认为最终答案立即显示，哪怕文字完全相同。中断或阶段未知沿用原生可见性规则。实时视图与重开历史共用折叠规则。历史上的四笔真实派发仍计四笔，旧记录缺少复用回执时保留原事实。[时间线分组](../../../../yijie-desktop/src/domain/conversation-activity-presentation.ts) · [现有原生预览归并](../../../../yijie-desktop/src-tauri/src/chat/native_conversation.rs)

## 4. 验收与启用

只读复核了杭州原记录。四次 Fetch 参数相同，剥离 Code Mode 耗时头后，四份交给模型的工具结果逐字段相同。按上述规则推演，首份结果建立证据，第二次请求触发纠偏，第三次仍照原轨迹请求才触发只作答。这个推演验证了该轨迹满足触发条件，产品行为以实施后的交互测试为准。

| 用例 | 通过条件 |
|---|---|
| 网关单独回放杭州四次同参取页 | 四个调用都收到对应回执，仅有一个原操作、一次实际对外发送，三个复用。改为并发时，等待者得到同一结果。 |
| 用可交互的本地模型重走现场顺序 | 模型逐步读到第一次返回的七天材料。夹入变化的托管搜索、空目标查询和不同措辞后，重复取页额外派发为零，纠偏最多一次。接受纠偏的模型产出按日期列出的七天预报、来源及实际缺项。持续只报进度的模型在补答上限内进入失败终态。两种分支均自动结束。 |
| 多城市、多个来源，同页分段摘取 | 各城市获得各自证据。新段落和并行任务都能正常交付。截断结果保留缺口，同参数读取仍返回原来的部分正文。 |
| 新轮刷新、正常重连、取消及结果不可用 | 新轮可以重新取页。正常重连后仍能证明归属时读取原操作。确认已派发或结果未知的调用额外发送为零。取消后没有新的补答或派发。 |
| 流式显示与历史重开 | 复现的相同进度正文只显示一次。新增细节即使位于句尾也完整显示。最终答案可独立阅读。展开过程可逐笔核对首次、等待、复用和历史真实派发。 |

拟实施按 `contract-impact = breaking` 评审，沿用 FEAT-175 的 `production_hardened / public`。现有闭合 schema 对 Pro 回执和结果有专门约束。先确定版本化契约、部署扩展数据库与兼容读端，再接入 Fetch 的 API、网关、Host 与 Runtime，最后在协商成功的新轮次启用纠偏和展示。已选新协议的轮次固定该版本，回退时停止接纳新的试用轮次，保留在途操作的幂等约束、只读查询及新旧历史读取能力。[既有设计与上线边界](41-deep-search-design-reaudit.md)

验收分别核对模型调用 ID、API 原操作、执行器实际发送、进入补答的次数、最终状态和桌面可见正文数。使用脱敏录制、可交互的本地模型和正常停止／重开覆盖上述分支。正式启用前，在任务授权额度内用正常桌面入口完成一次 Kimi 自然问答，检查回答质量与实际派发。以上数字为拟议放行标准。
