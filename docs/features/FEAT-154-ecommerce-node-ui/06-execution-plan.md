## 3. 步骤 1 的具体调查与定稿项

### 3.1 原生组件与节点标识

- 确定一个电商 UI 类别、30 个稳定 catalog key、每次添加的独立 instance ID；实例初值深复制。
- 明确 `WorkflowPlaygroundContext` 的模板 Map、`LocalWorkflowDocument` 的类型/数量限制和 Text 增删副作用如何与 UI 设计状态分开。
- 列出 `NodePanel/NodeList`、卡片、`NodeSideSheet`、本地搜索及注册器的最小修改位置；保留现有默认路径。
- 共用控件只覆盖当前文档需要的输入类型。不同节点通过前端展示元数据组织；不建立公共业务 Schema、运行引擎或通用低代码平台。

### 3.2 页面内配置与原草稿

- 按本稿推荐明确同一页面内保留，离开后不持久保存；这一点仍是 UI 方案建议，不追认为 PDF 明文或已批准决定。
- 逐一界定 `normalize/change/changeName`、撤销/重做、原生增删、重连读回、dirty 投影、返回/历史/路由/正常关闭的状态归属。
- 新 UI 图不进入可提交 DraftModel，也不放宽服务端三节点白名单；自动保存、快捷键与按钮使用同一保护条件。
- 设计状态在明确放弃后恢复原草稿和原有未保存内容；删除最后一个电商节点不自动恢复保存/运行能力。

### 3.3 契约影响与实施边界

- 只读核对 `yijie-contracts` 的现有 editor bridge 权威定义及 Desktop 消费者，确定 dirty/离开通知是否已涵盖不可保存的页面配置。
- 现有语义若完整涵盖，保留证据再把候选分类从 semantic 调整为 none；若需改变解释，按 source-first 补充适用源说明/检查及消费者；任何旧交互失效则升级 breaking。
- 不为纯 UI 增加商品/店铺/模型/媒体接口、native 权限或持久化格式。必要的 UI 离开保护协议工作与业务接口分开记录。
- 形成具体推荐方案后记录 D0 确认。当前用户只要求计划，不能因此把实现授权或 D0 改为通过。

验证围绕纯 UI：30 节点添加及侧栏、全部字段、实例不串值、空值区分、引用失效提示、普通输入纠正、取消离开、正常重连保留、未保存原草稿保护，以及新节点无业务请求。输出 status/report 字段仅看定义，不生成业务结果。

后续激活前先检查实际运行中的 App/未保存内容，再使用既有正常停止→标准构建→登记→恢复流程；保留原文件、未提交主题与数据。不得覆盖在线资源，不强杀、不破坏权限、不替换受保护 binary、不用攻击 fixture。无法正常停止即报告实际阻塞。

不新增长期 harness、全仓测试扩建或业务算法测试。只补保护共享状态和真实边界的聚焦检查；每次修复基于新事实。Git提交/推送、部署、真实平台和付费操作仍不包含在本次计划请求的执行范围。
