## 恢复入口的具体边界

### 拟改文件

- `yijie-infra/scripts/workflow-local.py`：复用精确归属、镜像、锁和正常stop能力；追加恢复预检/执行分支。
- `yijie-infra/Makefile`：提供明确命令入口，命名候选为`workflow-recovery-plan`与`workflow-recover`，目前尚不存在。
- `yijie-infra/scripts/workflow-local-model.mjs`及聚焦测试：固定阶段、重复调用和拒绝条件；测试采用普通内存状态/记录，不在真实环境制造异常。
- `yijie-infra/docs/workflow-local.md`：说明恢复适用条件、旧制品校验、恢复失败/正常退出与再次激活。
- API/Coze：优先使用已有只读能力；如需专用核验助手，由各自仓维护其存储语义。Infra仅编排，不自行决定业务终态。
- FEAT-154：记录恢复依据、执行结果与实际样板验收，保持可追踪。

### 阶段与资格

拟采用“预检完成→依赖恢复→操作核对→旧应用恢复→正常停止完成”。阶段先记录意图、执行后记录真实结果；重复命令先观察已有阶段与精确容器状态。中断后停在可核对状态，不自动从头重启。只有恢复阶段真实完成，才进入既有新候选激活顺序。

旧来源校验单独比对保存的容器image ID、旧注册bundle逐文件摘要、挂载和原epoch/配置；不使用当前1.4源码摘要冒充旧来源，也不放宽普通`verify_editor`。恢复期间保留旧bundle，待正常stop后才能生成新dist。

只选择原六个**主容器**。现有`coze-migrate`、`api-migrate`是一次性迁移容器，不参与恢复启动；不能按service名一把重启。原数据库用正常启动流程恢复，不设置强制恢复或跳过校验参数，不重跑迁移/业务操作。

操作核对须区分历史资格记录与未决业务：已知`storage qualification unknown`可逐ID与原证据对应，不要求所有历史unknown记录清零。未解释的recorded/unknown、非终态执行、active slot及查询失败均阻断应用恢复；不重发操作、不补写终态、不清占用。

恢复失败时保留当前阶段、原卷、容器及证据；已启动依赖只有确认没有业务在途后才能正常退出。正常退出仍无法完成则保持STOP_PENDING，停止后续步骤。原始异常不会因再次启动后的新退出码覆盖而从证据中消失。
