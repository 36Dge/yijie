# 跨境电商工作流节点定义：Listing 与搜索优化

## 9. 节点 9：Listing 综合诊断

### 9.1 目的与边界

以一个明确的平台、店铺、站点、locale、商品及不可变 Listing 版本为诊断对象，从身份与版本、结构完整度、搜索发现、内容与转化承接、素材一致性、合规与知识产权、价格／库存／履约、评价反馈和经营数据等维度，生成有证据的字段级问题、根因假设、严重程度与修复优先级，把“Listing 不好”转化为可执行的优化任务。

### 9.2 输入

| 变量名 | 类型 | 必选 | 说明 |
| --- | --- | ---: | --- |

### 9.3 处理逻辑

#### 步骤 1：锁定身份、版本与数据口径

1. 校验平台、店铺、市场、locale、seller SKU、父子／变体关系及类目是否属于同一目标；平台商品 ID／ASIN 已存在时必须匹配，未创建平台对象的草稿则以 seller SKU + draft artifact ID 锁定身份。任何跨站点、跨父子体或错 SKU 混合都先隔离。
2. 重算内容哈希与 `facts_hash`，锁定选定 Listing 基线、商品事实、规则版本、平台信号时间和各数据窗口；若提供 `keyword_asset`，同时锁定其 asset ID、version、hash、平台、站点、locale 和类目。诊断期间线上版本变化时返回 `LISTING_DIAG_BASELINE_CHANGED`，不把旧结论绑定到新版本。
3. 明确 `live` 与 `draft_precheck`：前者必须显式选择 live 基线，后者必须选择 draft 或 audit candidate 基线且不要求 live 存在。草稿没有真实流量和评价时，相关维度固定为 `not_applicable` 或 `not_diagnosed`；处于审核中的候选版本不得与 live 页面和旧流量拼成同一个基线。
4. 内容值以选定 `current_listing_snapshots` 基线为准；动态状态与平台 issue 采用“身份及内容版本匹配的最新平台来源”。去重键至少包含平台、seller／shop、marketplace、seller SKU、平台 product ID／ASIN（如有）、variant／子 SKU（如有）、platform code、字段路径和内容版本；不同实体的相同 code 不合并，只能在根因层聚合。两个来源指向不同版本或时间顺序矛盾时均保留并输出状态版本冲突，不用较新的时间戳静默覆盖不匹配版本。
5. 建立数据覆盖矩阵，逐项记录 `observed`、`platform_reported`、`seller_provided`、`derived` 或 `inferred`；缺权限、过期、抽样不足和口径不一致均降低覆盖率，而不是补零。
6. 若刚发生大幅内容、价格、库存、促销或投放变化，标记污染窗口，禁止把变化前后的相关性直接解释为本次 Listing 内容的因果效果。

#### 步骤 2：建立字段—事实—证据图

- 对标题、卖点、描述／A+、属性、规格、变体、图片 OCR、视频字幕／语音、价格、包装与履约信息做结构化解析，同时保留原始值；
- 建立 `field → claim → product_fact → evidence` 映射，核对品牌、型号、材质、数量、尺寸、单位、兼容性、性能、认证、适用人群和限制条件；
- 将所有原子声明汇总为 `effective_claim_ledger`，状态区分 `supported`、`unsupported`、`conflicting` 和 `unknown`；账本必须包含 `ledger_id`、`ledger_hash`、target、`facts_hash`、rule version、evidence snapshot hash、完整性状态，并为每条声明记录适用 SKU、字段、媒体位置、证据范围与有效期；
- 每个 finding 必须包含目标字段／SKU／媒体、观察值、预期条件、规则或证据引用、置信度和抓取时间；
- 平台返回的 issue、warning、audit／restriction 与内部规则分开存放，不能把内部启发式伪装成平台结论；
- 媒体模型、OCR 或 LLM 推断只能产生待核实线索，不能覆盖标准商品事实。

#### 步骤 3：诊断完整度、状态与基础可售性

1. 从当前 PTD／类目规则计算适用字段集合，分别检查 required、conditionally required、platform recommended 和 internal best practice；四类缺失不得使用同一严重度。
2. 完整度分母只包含当前市场、类目、商品形态和 SKU 真正适用的字段；不把“不适用”计为缺失，也不设置跨类目的固定字段数或字数。
3. 检查商品类型／叶子类目、品牌／GTIN、标题、核心属性、变体轴、尺寸表、媒体、认证和销售属性的缺失、非法枚举、错误格式及条件依赖。
4. 独立记录 live、buyable、discoverable、search suppressed、listing suppressed、audit、freeze 和平台问题严重度；“API 没有返回已定义 issue”不等于 Listing 没有其他问题。
5. 将阻断可售的问题与纯内容质量机会分开，避免总分平均后掩盖硬门禁。

#### 步骤 4：诊断搜索发现与关键词覆盖

1. 从商品类型、受支持属性、用途、受众、兼容对象和当地表达建立应覆盖的搜索意图集合；关键词必须回指商品事实。
2. 将关键词资产映射到标题、核心属性、卖点、描述及平台允许的搜索字段，检查核心概念缺失、字段错放、机械重复、无关高流量词、竞品品牌、语言混用和无证据声明。
3. 有真实查询数据时按 query／cluster 分析 `impression → click → cart → purchase`，区分站点、时间窗、organic、paid 和渠道归因；只有推荐词或模型扩展时标为 `inferred`，不得编造搜索量。
4. 低曝光只能产生相关性、索引、竞争或可售性等候选根因；只有字段缺失、平台 search suppression 或查询证据支持时，才提高内容根因置信度。
5. 输出 coverage gap 和 placement gap，不声称加入某词一定提升排名。

#### 步骤 5：诊断可读性、说服力与转化承接

- 检查信息层级是否让消费者快速理解“是什么、适合谁、解决什么问题、为何可信、如何选规格、如何使用以及有哪些限制”；
- 区分参数、消费者利益和证据，识别只堆参数、空泛形容、重复卖点、关键限定词缺失、过度承诺、错误单位、机械翻译和不符合 locale 的表达；
- 计算曝光、点击、加购、下单等漏斗，但只在同口径、同归因和满足样本门槛时比较历史或基线；低 CTR、低加购和低购买分别生成候选原因，不直接等同于标题、详情或价格导致；
- 将主图／标题、价值表达、价格、评分、配送承诺、库存和变体选择共同纳入转化诊断，避免把所有经营问题都归因于文案；
- 没有足够流量时仍可做结构质量诊断，但 `conversion_diagnostics.confidence` 必须降级。

#### 步骤 6：诊断跨字段、素材和变体一致性

构建 `CrossFieldFactMatrix`，逐项检查：

- 标题、卖点、描述／A+、属性、图片文字、视频文案和包装展示中的品牌、型号、材质、颜色、数量、尺寸、单位、兼容性、包含物和性能是否一致；
- 主图／首图是否展示正确商品，附图／视频是否误用其他变体、虚构配件或遮盖关键差异；
- 父体公共事实与子 SKU 专属事实是否混淆，媒体与变体是否保持一一映射；
- OCR 文案和字幕是否使用目标语言，数字、法定警示、认证和限制条件是否因翻译或裁切改变；
- 重复、低清、错误比例、主体不完整、过量文字等媒体问题按当前平台规则判定，不把固定模板跨站点复用。

任何商品身份、数量、规格或安全信息冲突都优先于 SEO 和文案美化问题。

#### 步骤 7：诊断合规、声明与知识产权风险

1. 按市场、叶子类目和商品事实检查禁限售、品牌／类目准入、危险品、年龄限制、成分、认证、制造商、责任人、安全标签和其他条件必填资料。
2. 对医疗健康、安全、环保、性能、比较、保证、原产地等声明逐条查验限定范围、证据、有效期和展示一致性；证据缺失即进入复核，不因竞品也这样写而放行。
3. 对品牌名、Logo、角色／名人、图片、视频、音乐、包装外观、专利／外观线索建立权利来源账本；无授权的第三方元素、混淆性兼容表达或“仿款／同款”线索提高风险。
4. 自动筛查只能输出 `risk_signal`，不能裁定侵权；高风险项交由权利或法务人员确认。
5. 平台质量诊断、预检或当前无处罚都不能替代完整合规／IP 审查；平台官方 issue 集也可能不是所有问题的全集。

#### 步骤 8：诊断价格、库存与履约干扰项

- 校验币种、销售价／划线价关系、价格异常、SKU 间价格范围、当前 Offer／Featured Offer 信号及促销时间；
- 按 SKU 检查可售、预留、在途、不可售和缺货状态，区分系统库存、平台库存及同步延迟；
- 检查 FBA／FBM 或 TikTok Shop 履约方式、包装尺寸重量、配送承诺与 Listing 表述是否一致；
- 将“内容问题”和“Offer／价格／库存／配送问题”分成不同根因组。例如有点击无下单且断货时，不能优先建议重写详情；
- 本节点只报告风险和依赖，不改价、不补库存、不切换履约。

#### 步骤 9：融合评价、退货和客服反馈

1. 规范化评价、退货、问答和客服主题，删除个人信息，记录站点、时间窗、样本量和来源可见范围。
2. 将“尺寸不符、配件缺失、颜色偏差、安装困难、适用范围误解”等主题映射到对应事实和 Listing 字段，识别“商品本身问题”与“页面预期管理问题”。
3. 只有重复出现且样本足够的主题才提高优先级；单条极端评价不直接成为确定根因。
4. 评价缺失、接口地区不支持或数据只提供聚合主题时，明确覆盖限制，不生成虚构评论摘要。

#### 步骤 10：根因归并与确定性优先级

- 将相同根因产生的多条平台 issue、规则失败、数据症状和评价主题去重，形成 `symptom → hypothesis → supporting/refuting evidence → confidence → affected fields` 根因图；
- 硬门禁优先于加权总分：P0 为实际不可售／搜索抑制、身份冲突、重大安全／合规或高置信 IP 风险；P1 为必填／关键事实缺失、严重本地化或可量化漏斗问题；P2 为有证据的搜索／转化机会；P3 为低影响可读性或样式问题；
- 同级优先级再按“影响范围 × 证据置信度 × 流量／收入暴露 × 修复可行性”排序，并考虑依赖关系；没有可靠指标时不给伪精确收益预测；
- 每个问题只给出修复 brief、责任角色、依赖、禁止改动项和完成判断，并标记 `remediation_domain` 与 `content_optimizable`；库存、价格、履约、身份、平台执法和合规／IP 问题不得进入内容优化范围。本节点不生成替换文案或可提交 payload；
- 输出前再次读取或比较内容哈希。基线变化则报告仍可供参考，但状态必须为 `stale` 或 `blocked` 并建议重跑。

### 9.5 输出

| 变量名 | 类型 | 说明 |
| --- | --- | --- |
| `meta` | `object` | 通用结果元数据、trace、模型／规则版本及开始结束时间 |
| `diagnosis_id` | `string` | 本次诊断唯一 ID |
| `diagnosis_state` | `string` | `complete`、`partial`、`stale` 或 `blocked` |

| `cross_field_matrix` | `object` | Listing、属性、变体、图片、视频、包装和商品事实的一致性结果 |

| `conversion_diagnostics` | `object` | 曝光到购买漏斗、样本充分性、内容与经营干扰项及候选原因 |

| `review_tasks` | `list<object>` | 需要卖家、运营、法务／合规或商品负责人确认的事项 |
| `data_quality_report` | `object` | 缺失、过期、权限、口径、归因、样本和污染窗口说明 |
| `optimization_scope` | `object` | 仅收录 `content_optimizable=true` 的 issue IDs、字段范围、锁定事实、关键词资产版本、保留项与禁止改动项；价格、库存、履约、身份、执法、合规／IP 问题不得进入，且不包含生成内容或平台提交指令 |

### 9.6 业务结果与错误码

| 代码 | 分类 | 默认处理 |
| --- | --- | --- |
| `LISTING_DIAG_SUCCESS` | 业务结果 | 返回完整覆盖范围内的问题、根因、优先级和审计证据 |
| `LISTING_DIAG_HEALTHY_BASELINE` | 业务结果 | 返回已覆盖维度“未发现显著问题”；不得表述为平台保证合规或保证增长 |
| `LISTING_DIAG_PARTIAL` | 业务结果 | 返回已确认问题和 `scope_coverage`，不为未诊断维度下结论 |
| `LISTING_DIAG_REVIEW_REQUIRED` | 复核 | 存在高风险声明、IP、身份或合规线索；生成审核任务，不自动修改 |
| `LISTING_DIAG_PERFORMANCE_SAMPLE_INSUFFICIENT` | 降级 | 保留静态诊断，漏斗和根因置信度降级 |
| `LISTING_DIAG_LISTING_NOT_FOUND` | 阻断 | 核对目标店铺、市场、商品 ID 和 seller SKU |
| `LISTING_DIAG_DATA_STALE` | 复核 | 标记过期来源；允许缓存时输出 partial，否则中断受影响维度 |
| `LISTING_DIAG_BASELINE_CHANGED` | 阻断 | 输出 `stale` 报告并基于新内容哈希重跑 |
| `LISTING_DIAG_IDENTITY_CONFLICT` | 阻断 | 隔离错站点、错 SKU、父子体或版本混用，不继续融合 |
| `LISTING_DIAG_FACT_CONFLICT` | 复核 | 保留冲突事实和来源，禁止生成确定性整改结论 |
| `LISTING_DIAG_INPUT_INVALID` | 致命 | 不重试；返回字段级校验错误 |
| `LISTING_DIAG_RULE_UNAVAILABLE` | 致命 | 无当前规则且没有允许、有效的缓存时停止，不能输出正式评分 |
| `LISTING_DIAG_PLATFORM_ACCESS_DENIED` | 降级 | 有可信快照时返回 partial；没有可信基线时阻断并提示授权范围 |
| `LISTING_DIAG_PLATFORM_THROTTLED` | 可重试 | 遵守平台重试提示和指数退避；超过预算后返回 partial，不伪造实时信号 |
| `LISTING_DIAG_UPSTREAM_UNAVAILABLE` | 可重试 | 平台或数据源短暂失败时重试；仅在缓存仍有效时降级 |
| `LISTING_DIAG_OUTPUT_SCHEMA_INVALID` | 致命 | 不返回不可审计的自由文本结果 |

## 10. 节点 10：Listing 一键优化

### 10.1 目的与边界

一次运行生成 Amazon 或 TikTok Shop 的完整 Listing 草稿、字段级变更和审核任务。该节点是子流程编排器，不负责发布，不绕过人工审核，也不把“生成完成”标记为“平台合规/审核通过”。

### 10.2 输入

| 变量名 | 类型 | 必选 | 说明 |
| --- | --- | ---: | --- |
| `product_snapshot` | `object` | 是 | 不可变标准商品事实快照；运行前重算 `facts_hash` |
| `target` | `object` | 是 | 一次只处理一个平台、站点和 locale；多目标由 Batch 展开 |
| `rule_bundle_ref` | `string` | 是 | 当前目标规则快照 |
| `current_listing_snapshots` | `list<object>` | 条件必选 | 老品、已有 draft／audit candidate，或提供 `diagnosis_result` 时必选，并包含节点 9 所诊断的不可变基线，使节点 10 可重算 content hash；老品必须含 live，其他版本仅在实际存在时传入。只有不使用诊断结果、从零生成的纯新品可省略 |
| `diagnosis_result` | `object` | 否 | 节点 9 输出；仅消费其 `optimization_scope` 中 `content_optimizable=true` 的 issue，不能把价格、库存、履约、身份、执法、合规／IP 等 P0/P1 当作内容改写任务 |
| `keyword_asset` | `object` | 条件必选 | 节点 11 完整输出；`full_generate` 缺失时可内部调用相同组件，`assemble_only` 任一组件引用关键词时必须显式提供并核对 ID/version/hash |
| `claim_ledger` | `object` | 条件必选 | `full_generate` 缺失时可从事实构建；`assemble_only` 必须由本字段或 `diagnosis_result.effective_claim_ledger` 提供完整账本 |
| `competitor_gaps` | `list<object>` | 否 | 只用于识别差异化机会，不复制受保护表达 |
| `brand_voice` | `object` | 否 | 语气、品牌术语、禁用表达和样例 |
| `media_assets` | `list<object>` | 否 | 详情/A+ 可用图片、视频、Alt 文本证据 |
| `variant_builder_artifact` | `object` | 条件必选 | `full_generate` 涉及变体文案时必选；封装第一阶段 `VariantBuilderOutputV1`、稳定 payload hash 及排除路径 |
| `optimization_config` | `object` | 是 | 模式、字段范围、候选数、保留字段、审核门槛和组件版本 |
| `execution_mode` | `string` | 是 | `full_generate` 或 `assemble_only` |
| `component_outputs` | `object` | 条件必选 | `assemble_only` 时使用强类型 `title_result/selling_point_result/detail_result/variant_copy_result`；只接收节点 12、13、14、16，不包含节点 15 |

### 10.3 处理逻辑

#### 步骤 1：目标和版本锁定

1. 锁定商品事实哈希、`live/audit_candidate/draft` 快照集、被显式选定的 Listing 基线哈希、规则包、关键词资产和各生成组件版本。
2. 如提供 `diagnosis_result`，必须从 `current_listing_snapshots` 取得被诊断的不可变基线并重算 content hash；缺少匹配基线时拒绝消费。随后核验 diagnosis state、target、facts hash、rule version 和关键词 asset ID／version／hash：`stale` 或 `blocked` 一律拒绝；`partial` 只接受 `scope_coverage=diagnosed`、基线仍匹配且证据完整的相关 issue；只消费 `optimization_scope` 中 `content_optimizable=true` 的 issue。
3. 复用 `diagnosis_result.effective_claim_ledger` 时，必须重算并核对 ledger ID／hash、target、facts hash、rule version、evidence snapshot hash 和完整性状态；不匹配时不得降级为“可信账本”。
4. 检查这些对象的平台、站点、类目、locale 是否一致；不一致时不静默复用。
5. 老品若线上快照在工作流期间变化，输出 `OPTIMIZE_BASELINE_CHANGED`，禁止生成可直接应用的 PATCH。
6. 确定 `new_listing`、`full_rewrite`、`selected_fields` 或 `minimal_fix` 模式。
7. 如存在未决 `audit_candidate`，默认只能输出 `draft_only` 或阻断，不得基于较旧 live 版本生成可应用 PATCH。

#### 步骤 2：建立内容蓝图

- 从商品类型、核心用户任务、事实、差异化证据和购买疑虑建立 message hierarchy；
- 为每个事实分配可用字段，避免标题、五点和描述逐字重复；
- 将核心词、属性词、场景词和长尾词分配到允许字段；
- 建立“必须保留”“允许改写”“禁止生成”“需补证据”的字段清单；
- Amazon 与 TikTok Shop 分别建立蓝图，不通过简单翻译互转。

#### 步骤 3：复用字段组件

`full_generate` 模式按同一版本调用：

1. SEO 关键词挖掘组件；
2. 商品标题优化组件；
3. 卖点/五点生成组件；
4. 详情/A+ 生成组件；
5. 规格与变体文案组件。

`assemble_only` 模式不再次生成，而是消费已运行的节点 12、13、14、16 结果，校验其事实哈希、目标、关键词资产和规则版本后组装。节点 15 始终位于完整内容包组装之后，不能作为节点 10 的输入组件，从而避免环依赖。若目标语言需要转换，先完成节点 10，再运行节点 15。相同输入哈希、规则和组件版本应得到兼容结果；一键节点输出每个组件的 `component_trace`，不能只返回最终长文本。

#### 步骤 4：候选生成与约束选择

- 每个关键字段先生成多个结构化候选；温度保持低且记录模型版本/seed（模型支持时）。
- 候选必须通过事实引用、平台规则、禁词、长度、Unicode/字节计量、HTML 和跨 SKU 真值校验。
- 排序只在通过硬门禁的候选中进行；建议目标为搜索意图覆盖、可读性、差异化、信息完整度和改动幅度。
- 无候选通过时返回 `needs_review` 和失败约束，不用截断或删除限定词硬凑一个结果。

#### 步骤 5：跨字段一致性

构建 `CrossFieldFactMatrix`，逐项检查：

- 品牌、型号、数量、材质、尺寸、单位、兼容性在各字段是否一致；
- 标题中的核心承诺是否在卖点或详情有事实解释；
- 详情/A+ 是否引入标题和五点中不存在的新产品事实；
- 变体特定值是否错误提升到父商品；
- 关键词是否自然使用且语义未被改写成不同声明；
- Amazon 标准描述与 A+、TikTok Shop 描述与商品属性是否矛盾。

#### 步骤 6：安全与人工审核门禁

以下至少进入 `needs_review`：

- 品牌授权、认证、医疗/健康、安全、环保、性能、比较或保证声明证据不足；
- 关键商品事实冲突；
- 目标规则包过期或回退到通用规则；
- 对线上商品做了身份级变化，如实质改变型号、数量、材质或产品用途；
- 大比例语义重写且没有清晰基线；
- 本地化存在未决关键术语、数值或法定标签。

#### 步骤 7：输出变更集与回滚基线

- 对每个字段输出 `before`、`after`、规范化 diff、原因、issue/keyword/claim 引用；
- 提供 `apply_eligibility=ready_for_review|review_required|blocked`，它只表示当前草稿是否可进入人工审核；不等于 Listings Restrictions 通过、Validation Preview 无误、提交 `ACCEPTED` 或异步生效；
- 输出平台 payload preview：可提交预览包含 endpoint、API version、method、partial/full edit mode、结构化字段值、preserved fields、baseline version 与不可变 payload artifact；`draft_only` 有结构化草稿 artifact，但不伪造 endpoint/method；
- Amazon 完整候选请求在接口可用时执行 Validation Preview。TikTok Shop 只有 `new_listing` 的完整候选执行 Check Product Listing；`full_rewrite/selected_fields/minimal_fix` 老品只按当前 Edit/Partial Edit Schema 做预提交校验，平台接受性须在后续真实提交响应、audit 状态和 webhook 中确认。未执行适用检查、超时或结果过期时，`apply_eligibility` 不得被解释为平台可接受。
- 保存 `baseline_hash`，后续发布节点只有基线仍一致才可应用；
- 对未改字段明确输出 `preserved`，防止部分更新接口把空值当删除。
- TikTok Shop 老品的 `listing_platforms` 从选定基线快照原样保留；无法读取现值时不得生成 `validation_state=valid` 的编辑预览。只有新品才允许显式选择平台集合。

### 10.4 输出

| 变量名 | 类型 | 说明 |
| --- | --- | --- |
| `meta` | `object` | 通用结果元数据 |
| `optimization_id` | `string` | 本次优化 ID |
| `effective_claim_ledger` | `object` | 本次各字段共同使用的完整声明账本；内部构建时也必须返回 |
| `optimization_state` | `string` | `generated`、`baseline_preserved` 或 `no_valid_candidate` |
| `content_package` | `object` | 条件输出；有有效候选或可明确保留的基线时才返回 `ListingContentPackageV1` |
| `change_set` | `list<object>` | 字段级前后值、原因和证据 |
| `component_traces` | `list<object>` | 关键词、标题、卖点、详情、变体组件的版本、输入/输出哈希与结果引用；不包含后续节点 15 |
| `validation_report` | `object` | Schema、事实、声明、关键词、跨字段和渲染校验 |
| `review_tasks` | `list<object>` | 人工确认项 |
| `payload_previews` | `list<object>` | 条件输出；每个 HTTP 请求一个强类型预览，含依赖顺序，不含凭证、不执行提交；Listing、A+ 文档和 ASIN relations 可同时存在 |

| `platform_readiness` | `object` | 结构就绪、上架资格、预检、提交和异步处理的分离状态 |

## 11. 节点 11：SEO 关键词挖掘

### 11.1 目的与边界

从商品事实、真实搜索数据、平台推荐、竞品和用户语言中构造可审计关键词资产，并给出字段放置计划。节点不爬取未授权数据，不把推断词标成真实热度，也不输出“使用后一定提升排名”。

### 11.2 输入

| 变量名 | 类型 | 必选 | 说明 |
| --- | --- | ---: | --- |
| `product_snapshot` | `object` | 是 | 不可变标准商品事实快照；运行前重算 `facts_hash` |
| `target` | `object` | 是 | 平台、市场、locale、类目/商品类型 |
| `rule_bundle_ref` | `string` | 是 | 字段、禁词和计量规则 |
| `seed_terms` | `list<object>` | 否 | 卖家种子词，含原始语言和来源 |
| `first_party_observations` | `list<object>` | 否 | Amazon Brand Analytics/广告 Search Term 或 TikTok Shop 搜索/SEO 数据；必须标明数据表面与样本条件 |
| `official_recommendations` | `list<object>` | 否 | 平台官方推荐词及获取时间 |
| `competitor_corpus` | `list<object>` | 否 | 可比竞品标题/卖点/属性；需带商品、站点和采集时间 |
| `review_corpus` | `list<object>` | 否 | 评论/问答主题及样本范围，不含个人标识 |
| `existing_keyword_asset` | `object` | 否 | 增量更新时使用 |
| `keyword_config` | `object` | 是 | 来源优先级、意图分类、评分权重、最低证据、最大候选数和放置策略 |

### 11.3 处理逻辑

#### 步骤 1：来源验收

- 校验站点、locale、窗口、指标单位和授权范围；
- 同一 query 在不同匹配类型、广告组或时间窗的记录不直接相加；
- Amazon 广告 Search Term 必须记录 campaign/ad group/match type、`selection_condition`与 `query_origin`；当前报表只覆盖至少有一次广告点击的词，且可能包含非搜索场景推断的 best match，缺失行不代表零需求；
- `brand_analytics`、`paid_ads`、`backend_generic_keyword` 是不同 data surface；付费观测不直接充当自然搜索量，平台后台 Generic Keyword 又是可编辑字段而非观测。
- 记录 observed、platform_recommended、derived、inferred 四种来源语义；
- 过期数据可用于语言发现，但不能代表当前热度；
- 跨平台语料只可作为候选发现，必须在目标平台重新验证。

#### 步骤 2：规范化但保留原词

执行 Unicode 规范化、空白/标点整理、大小写折叠、语言检测、单复数/词形分析和单位同义化。每条记录同时保留：

- `raw_phrase`：来源原文；
- `normalized_phrase`：去格式差异后的形式；
- `canonical_concept_id`：相同概念聚类 ID；
- `surface_forms`：目标 locale 可用表达。

品牌、型号、专有名词和兼容对象不得被普通 stemming 破坏。

#### 步骤 3：候选扩展

候选来源包括：

- 商品类型、属性、功能、材质、尺寸、数量；
- 用户问题、使用场景、受众和兼容对象；
- 真实搜索词与平台推荐词；
- 竞品共现词与评论自然语言；
- 同义词、常见缩写、当地单位表达和语序变体。

LLM 只能扩展 C 级候选，必须标为 `inferred`；没有真实观测时不得填搜索量。

#### 步骤 4：商品相关性硬门禁

每个词都要映射到事实或允许的用户意图：

```text
relevance = product_type_match
          + supported_attribute_match
          + supported_use_case_match
          + audience_or_compatibility_match
          - ambiguity_penalty
          - unsupported_claim_penalty
```

以下默认排除或复核：竞品品牌、自有品牌在平台禁止放置的字段、无关高流量词、无法证明的材质/功效/兼容词、促销及时效词、成人/敏感/监管词、错误拼写诱导、ASIN/商品 ID 堆砌。

#### 步骤 5：意图与语义角色分类

每个词至少标记：

- 购买意图：核心品类、属性筛选、用途/问题、受众、兼容、场景、比较/替代、信息咨询；
- 漏斗阶段：高意图、评估、探索；
- 语义角色：`product_type`、`feature`、`material`、`size_pack`、`audience`、`use_case`、`problem`、`compatibility`、`occasion`；
- 商品适配范围：全商品或具体 SKU；
- 风险：普通、需事实、需合规、禁止。

#### 步骤 6：聚类和去重

- 同一概念的单复数、词序变体、缩写保留各自观测，但共享 cluster；
- 不把不同意图的近义词强行合并，例如“travel bottle”和“bottle for toddler”可能对应不同受众；
- 对可组合词建立 token coverage，避免为了覆盖所有长尾而机械重复完整短语；
- 识别同义词冲突、语言混用和关键词蚕食，但不声称平台一定按相同方式索引。

#### 步骤 7：确定性评分

默认只作为可配置示例：

```text
keyword_priority =
    0.35 × relevance_score
  + 0.20 × first_party_demand_score
  + 0.15 × conversion_evidence_score
  + 0.10 × official_recommendation_score
  + 0.10 × differentiation_score
  + 0.10 × evidence_quality_score
```

- 缺失维度不按 0；覆盖足够时重分配权重，否则不给正式分数；
- 指标先按同站点、同窗口、同口径稳健归一；paid 与 organic 始终分层计分，不在没有校准的情况下合并；
- 高搜索量但低相关性不能通过硬门禁；
- 平台推荐只是一项证据，不自动成为标题词；
- 分数是放置优先级，不是排名概率。

#### 步骤 8：字段预算分配

把通过门禁的词分配为：

- `must_cover`：核心商品类型和高证据高意图概念；
- `should_cover`：关键属性、场景和差异化概念；
- `optional`：长尾或内容扩展；
- `excluded`：记录原因，避免下游重新生成。

Amazon 分支按规则包将词分配到 Item name、Item highlights、bullet points、描述、属性和可用 Generic Keyword，并用实际字符/字节计量器做背包选择；真实 API 属性路径始终由 PTD 发现。TikTok Shop 分支优先把官方相关词和高意图词自然放入标题，其余放入 Product Highlights、描述或后续短视频内容词池；只有 capability 明确支持的市场才生成 `search_terms` API patch。

#### 步骤 9：质量与可审计性

输出来源覆盖率、A/B/C 级比例、有数值指标比例、过期率、被排除数量、语言覆盖和未覆盖的核心概念。任何数值指标都附时间窗、单位和 evidence ID。

### 11.4 输出

| 变量名 | 类型 | 说明 |
| --- | --- | --- |
| `meta` | `object` | 通用结果元数据 |
| `keyword_asset` | `object` | `KeywordAssetV1`，含候选、词群、意图、分数、证据和完整 exclusion ledger，防止下游重新引入排除词 |
| `placement_plan` | `list<object>` | 平台字段、词群、优先级、预算成本和理由 |
| `excluded_terms` | `list<object>` | 原词、排除原因、风险和证据 |
| `source_coverage` | `object` | 来源等级、窗口、指标和新鲜度概况 |
| `unresolved_concepts` | `list<object>` | 事实不足、歧义或需本地专家确认的概念 |

### 11.5 业务结果与错误码

| 代码 | 分类 | 默认处理 |
| --- | --- | --- |
| `KEYWORD_NO_FIRST_PARTY_DATA` | 业务结果 | 允许 B/C 级资产，但不输出热度结论 |
| `KEYWORD_NO_VALID_TERM` | 业务结果 | 返回空可用词和排除原因 |
| `KEYWORD_METRIC_NOT_COMPARABLE` | 警告 | 隔离不兼容窗口/单位 |
| `KEYWORD_LOW_SOURCE_COVERAGE` | 复核 | 可供草稿使用，但禁止热度型结论 |
| `KEYWORD_INPUT_INVALID` | 致命 | 不重试 |
| `KEYWORD_AUTH_FAILED` | 致命 | 不重试 |
| `KEYWORD_RULE_CONFLICT` | 复核/部分成功 | 停止受影响字段放置，保留可审计的候选发现结果；只有无任何可返回结果时才走异常分支 |

## 12. 节点 12：商品标题优化

### 12.1 目的与边界

在产品事实、目标语言和平台约束内生成、改写或压缩标题，兼顾商品识别、搜索意图覆盖和消费者可读性。节点不通过堆砌词、竞品品牌、虚构功效或删除必要限定词换取更高表面分数。

### 12.2 输入

| 变量名 | 类型 | 必选 | 说明 |
| --- | --- | ---: | --- |
| `product_snapshot` | `object` | 是 | 不可变商品事实和变体快照 |
| `target` | `object` | 是 | 平台、站点、locale、类目/商品类型 |
| `rule_bundle_ref` | `string` | 是 | 标题长度、字符、重复、模板和类目规则 |
| `keyword_asset` | `object` | 是 | 目标语言关键词资产 |
| `claim_ledger` | `object` | 是 | 可用声明及限定条件 |
| `current_title` | `object` | 否 | 改写/压缩/最小修复模式的 `ContentUnitV1` |
| `current_amazon_item_highlights` | `object` | 否 | Amazon 老品改写时与 Item name 一起读取，用于迁移和去重 |
| `protected_tokens` | `list<object>` | 否 | 品牌、型号、标准缩写、商标大小写及不可翻译片段 |
| `optimization_brief` | `object` | 否 | 人工确认后的可编辑路径、目标 issue、锁定片段和改动预算 |
| `title_config` | `object` | 是 | 生成模式、候选数、最小改动、目标槽位、评分权重和人工锁定片段 |

### 12.3 处理逻辑

#### 步骤 1：标题槽位建模

从事实和关键词资产构建槽位，而不是直接让模型自由写作：

```text
identity: authorized_brand + product_type + model
differentiation: supported_core_feature + material + capacity/pack
fit: audience + use_case + compatibility
variant_boundary: PARENT=shared facts; CHILD=shared identity + selected child facts; NONE=standalone facts
```

每个槽位记录 `required/optional/prohibited`、事实路径、关键词 cluster、字符成本和跨 SKU 适用范围。

#### 步骤 2：平台与类目模板

- 模板来自规则包和目标 locale，不把固定英文顺序套给所有市场；
- Amazon 先由 PTD/类目模板确认字段能力和真实属性路径，再应用当前生效的标题政策硬约束；类目风格与最佳实践只参与候选排序，不作为 Schema blocker；
- TikTok Shop 优先包含品牌（有授权时）、商品类型、必要识别信息和核心特征，并把只属于 SKU 的颜色/尺寸留在变体标签；
- 品牌未知或未授权时不生成品牌；不能用卖家名补位。

#### 步骤 3：生成候选

可采用受约束模板、beam search 或低随机性 LLM 生成 3～8 个候选。每个候选同时输出 segment 数组，说明每段来自哪个事实和词群。模型不能自行增加数量、材质、性能、适配对象或促销。

#### 步骤 4：确定性规范化与计量

1. Unicode 标准化、空白折叠和标点修正；
2. 使用规则指定的字符、Unicode code point、UTF-8 byte 或其他计量单位；
3. 检查最小/最大长度、禁止字符、大小写、重复词、促销词、库存词、时效词和主观绝对化词；
4. 保护型号、合法品牌字符和标准单位，不能粗暴删除；
5. 超长时按低优先级槽位整段删除或改写，不能从中间截断词或丢失限定条件。

#### 步骤 5：候选硬门禁

候选必须同时满足：

- 所有产品声明可回溯到 `ClaimLedgerV1`；
- 标题事实对所有适用 SKU 成立；
- 核心商品类型存在且不歧义；
- 没有竞品品牌、平台未授权徽标、联系方式、促销/库存/配送承诺；
- 当前平台/站点/类目 Schema 通过；
- 语言检测符合目标 locale，数字和单位与事实一致。

#### 步骤 6：多目标排序

只对通过硬门禁的候选计算启发式质量：

```text
title_quality =
    search_intent_coverage
  + product_identification
  + readability
  + differentiation
  + locale_naturalness
  - redundancy
  - ambiguity
  - change_risk
```

各项归一到同一范围并由版本化策略加权。`change_risk` 在老品最小改动模式中权重更高。输出各维度和原始覆盖，不能只返回一个总分。

#### 步骤 7：删减和遗漏解释

输出哪些候选词未进入标题及原因：已在其他字段覆盖、相关性不足、字符预算不足、变体专属、证据不足或平台禁止。这样下游不会再次把这些词塞回标题。

### 12.4 输出

| 变量名 | 类型 | 说明 |
| --- | --- | --- |
| `meta` | `object` | 通用结果元数据 |
| `selected_title` | `object` | 条件输出；有通过硬门禁的候选时才存在，含 segment、计数和 claim/keyword/evidence 引用 |
| `amazon_item_highlights` | `object` | Amazon 目标且 capability 支持时输出；包含真实字段路径、文本和校验 |
| `alternatives` | `list<object>` | 通过门禁的备选标题和维度得分 |
| `rejected_candidates` | `list<object>` | 候选、失败规则和字段证据 |
| `coverage_report` | `object` | 核心概念覆盖、重复度、可读性和本地语言检查 |
| `omitted_terms` | `list<object>` | 未放入标题的词及原因 |
| `change_summary` | `object` | 与当前标题的差异、变更风险和建议审核级别 |

### 12.6 业务结果与错误码

| 代码 | 分类 | 默认处理 |
| --- | --- | --- |
| `TITLE_CURRENT_ALREADY_PREFERRED` | 业务结果 | 返回现标题为选定结果，无修改 |
| `TITLE_NO_VALID_CANDIDATE` | 复核 | 返回全部失败约束，不截断硬凑 |
| `TITLE_REQUIRED_FACT_MISSING` | 复核 | 缺品牌/类型等关键事实时停止自动采用 |
| `TITLE_VARIANT_SCOPE_CONFLICT` | 复核 | 移除 SKU 专属声明或要求人工确认 |
| `TITLE_INPUT_INVALID` | 致命 | 不重试 |
| `TITLE_RULE_UNAVAILABLE` | 致命 | 没有允许的规则缓存时中断 |
| `TITLE_OUTPUT_INVALID` | 致命 | Schema/编码异常时中断 |

## 13. 节点 13：核心卖点／五点描述生成

### 13.1 目的与边界

把商品参数转化成消费者可以理解、且有事实支持的购买理由。Amazon 分支输出当前规则允许的 `bullet_point`；TikTok Shop 分支输出商品 highlights/卖点块并按能力映射到可用字段，不强制伪装成“五点”。

节点不以“凑够五条”为目标。事实只支持三条时就输出三条并列出缺口；评论痛点只能决定讲述顺序，不能证明自有商品解决了该问题。

### 13.2 输入

| 变量名 | 类型 | 必选 | 说明 |
| --- | --- | ---: | --- |
| `product_snapshot` | `object` | 是 | 不可变商品事实、属性、包装内容和变体快照 |
| `target` | `object` | 是 | 平台、市场、locale、类目/商品类型 |
| `rule_bundle_ref` | `string` | 是 | bullet/highlight/描述块的当前规则与能力 |
| `claim_ledger` | `object` | 是 | 允许、受限、禁止声明及证据 |
| `keyword_asset` | `object` | 否 | 用于自然覆盖，不以堆词为目的 |
| `audience_context` | `object` | 否 | 目标人群、购买任务、使用阶段；必须与事实和市场相容 |
| `review_insights` | `list<object>` | 否 | 用户痛点主题、样本量和证据 |
| `competitor_gaps` | `list<object>` | 否 | 可比竞品内容空白，不含可复制表达 |
| `current_selling_points` | `list<object>` | 否 | 改写或最小修改使用 |
| `optimization_brief` | `object` | 否 | 人工确认后的可编辑路径、目标 issue、锁定片段和改动预算 |
| `selling_point_config` | `object` | 是 | 目标条数、主题权重、结构、重复阈值、候选数和品牌语气 |

### 13.3 处理逻辑

#### 步骤 1：构建声明图

将可用事实连接成：

```text
fact/attribute
  → product_function
  → mechanism_or_reason
  → customer_benefit
  → usage_context
  → evidence/qualifier
```

例如“容量 500 ml”是事实；“减少频繁补水”是可能的用户利益；它不能被扩写为“全天无需补水”。每个利益表达必须保留适当限定，且能回溯到事实或经确认的常识规则。

#### 步骤 2：主题候选与选择

候选主题包括核心功能、关键规格、材质/工艺、易用性、兼容性、包装内容、维护、安全注意和差异化。主题优先级考虑：

- 对购买决策的重要度；
- 商品与竞品的真实差异；
- 评论痛点的频率与严重度；
- 证据强度；
- 标题和详情的已有覆盖；
- 是否适用于所有相关 SKU。

评论主题只有在商品事实确实支持解决方案时才增加优先级；否则成为产品改进或待补证据，而不是卖点。

#### 步骤 3：最大边际相关性去重

不是简单计算文本相似度，而是按“用户问题 + 事实 + 利益”三层去重。每新增一条卖点，都要最大化新增信息：

```text
MMR(theme) = importance × evidence_strength
             - redundancy_with_selected
             - unsupported_scope_risk
```

同一事实可以在不同字段出现，但不能让五条只是同一句的改写。

#### 步骤 4：结构化生成

每条先生成结构对象，再渲染文本：

```json
{
  "theme": "capacity_and_portability",
  "feature": "500 ml capacity",
  "benefit": "holds a practical amount for daily carry",
  "proof_or_qualifier": "measured product capacity",
  "claim_ids": ["claim-capacity-500ml"],
  "keyword_cluster_ids": ["cluster-reusable-bottle"],
  "sku_scope": "all_variants"
}
```

标题式前缀、完整句、标点和长度由目标规则包决定。参数不能被模型重新计算；比较、性能、保证、健康、安全和环保声明必须通过相应声明门禁。

#### 步骤 5：平台渲染

**Amazon：**

- 映射到目标 PTD 的 `bullet_point` 或等效字段；
- 条数、顺序、字符、特殊字符和禁止短语从当前规则读取；
- 优先表达关键特征与利益，避免价格、优惠、配送、退款保证、联系方式和竞品贬损；
- Amazon 官方曾更新 bullet point 的字符、emoji 和部分短语规则，因此节点不能固化旧样式。[Amazon 官方 Bullet Point 规则更新公告](https://sellercentral.amazon.com/seller-forums/discussions/t/65f8e647-977d-49ac-9036-2049b96720b2)

**TikTok Shop：**

- 若目标市场/接口支持 Product Highlights 或 `key_product_features`，按 capability 和实时 Schema 输出；
- capability=`unsupported` 时生成 `fallback_description_block`，由详情节点渲染进描述；capability=`unknown` 时只返回候选、`needs_review` 和能力缺口，不得进入 payload；
- 与标题、商品属性和 SKU 值一致，不混入短视频口播、hashtag 或达人脚本；
- Academy 建议和 API 接收范围属于不同层：前者生成质量提醒，后者才是硬阻断。

#### 步骤 6：逐条校验

1. 抽取最终文本中的原子声明并回查 `claim_id`；
2. 检查数字、单位、否定词、条件词和 SKU 范围；
3. 检查竞品品牌、促销、保证、退款、时效、绝对化和监管高风险表达；
4. 检查关键词是否自然、是否改变句义；
5. 检查跨条重复、跨字段矛盾和本地语言自然度；
6. 任何自动修复都重新执行完整校验，最多两轮。

### 13.4 输出

| 变量名 | 类型 | 说明 |
| --- | --- | --- |
| `meta` | `object` | 通用结果元数据 |
| `selling_points` | `list<object>` | 文本、结构、顺序、claim/keyword/evidence 和适用 SKU |
| `amazon_bullet_points` | `list<object>` | Amazon 目标时输出，每条带内容、声明、关键词与证据；非 Amazon 标为不适用 |
| `tiktok_product_highlights` | `list<object>` | 能力支持时输出，每条带内容和 lineage |
| `fallback_description_block` | `object` | TikTok Shop 不支持独立 highlights 时使用 |
| `coverage_matrix` | `list<object>` | 主题、事实、用户问题和关键词覆盖 |
| `rejected_claims` | `list<object>` | 无证据、受限或禁止声明及原因 |
| `validation_report` | `object` | 长度、规则、事实、重复和跨 SKU 校验 |

### 13.5 业务结果与错误码

| 代码 | 分类 | 默认处理 |
| --- | --- | --- |
| `SELLING_POINT_FEWER_THAN_TARGET` | 业务结果 | 输出有证据条目，不编造补齐 |
| `SELLING_POINT_NO_DIFFERENTIATOR` | 业务结果 | 生成基础事实型卖点并标记产品差异不足 |
| `SELLING_POINT_CAPABILITY_UNAVAILABLE` | 业务结果 | TikTok Shop 回退描述块 |
| `SELLING_POINT_CLAIM_NEEDS_EVIDENCE` | 复核 | 排除相关声明并返回补证据任务 |
| `SELLING_POINT_VARIANT_SCOPE_CONFLICT` | 复核 | 限定到 SKU 或停止使用 |
| `SELLING_POINT_INPUT_INVALID` | 致命 | 不重试 |
| `SELLING_POINT_OUTPUT_INVALID` | 致命 | 不返回未校验文本 |

## 14. 节点 14：商品详情描述／A+ 内容生成

### 14.1 目的与边界

生成结构化长详情，解释商品价值、规格、使用、限制和常见疑问；Amazon 在资格与能力明确时生成 A+ Content 模块方案，TikTok Shop 生成商品描述及类目信息模块。

本节点不生成图片，不伪造 A+ 资格，不把任意 HTML 当作 Amazon A+，也不把价格、库存、促销等易过期 Offer 信息写进长期商品内容。

### 14.2 输入

| 变量名 | 类型 | 必选 | 说明 |
| --- | --- | ---: | --- |
| `product_snapshot` | `object` | 是 | 不可变商品事实、属性、包装、变体和使用信息快照 |
| `target` | `object` | 是 | 平台、站点、locale、类目/商品类型 |
| `rule_bundle_ref` | `string` | 是 | 描述字段、HTML、A+ 模块、图片和类目规则 |
| `claim_ledger` | `object` | 是 | 可用声明及限定条件 |
| `keyword_asset` | `object` | 否 | 详情词群，不能主导事实 |
| `selling_points` | `list<object>` | 否 | 节点 13 输出，用于互补和去重；精细流程中建议明确为 13 → 14 |
| `media_assets` | `list<object>` | 否 | 已存在的图片/视频引用、权利状态、尺寸和内容标签 |
| `a_plus_context` | `object` | 否 | Amazon 的资格/状态、contentReferenceKey、当前与目标全量 ASIN 集合及哈希、完整快照、移除审批和 API 模型 |
| `faq_inputs` | `list<object>` | 否 | 用户真实问题或卖家提供的 FAQ；答案仍需事实支持 |
| `current_detail` | `object` | 否 | 现有标准描述/A+/TikTok Shop HTML 描述 |
| `optimization_brief` | `object` | 否 | 人工确认后的可编辑路径、目标 issue、锁定内容和改动预算 |
| `detail_config` | `object` | 是 | 内容目标、模块偏好、最大模块数、重复阈值和资产策略 |

### 14.3 处理逻辑

#### 步骤 1：选择内容模式

```text
Amazon + confirmed A+ capability/eligibility → a_plus_plan + standard fallback
Amazon + eligibility unknown/not eligible   → standard_description
TikTok Shop                                  → structured_description_html
```

“未验证资格”与“确定不符合资格”要区分。A+ 不可用是正常业务结果，不触发系统异常。

#### 步骤 2：建立信息架构

根据类目和商品复杂度，从以下模块中选择必要项：

1. 商品是什么、面向谁；
2. 关键利益及其事实依据；
3. 使用场景与使用方法；
4. 尺寸、容量、材质、成分、兼容和包装内容；
5. 安装、清洁、保养和存储；
6. 安全、限制、警示或适用边界；
7. FAQ；
8. 自有商品系列比较（仅有一致、可验证维度时）。

模块选择不是“越多越好”。按购买疑虑覆盖、事实可用性、资产可用性和页面预算求解；没有内容增益的模块不生成。

#### 步骤 3：内容与资产匹配

- 先读取媒体的角色、尺寸、比例、语言、权利和产品一致性；
- 模块要求图片但没有合格资产时，输出 `asset_requirement`，不创建虚假 URL；
- Alt text 描述图中可见内容，不塞入不可见关键词；
- 图片含文案时检查语言与产品事实，OCR 不确定则人工复核；
- 只有自有或有权使用的素材才能进入 payload preview。

#### 步骤 4：生成模块草稿

每个模块由固定字段构成：

- `module_purpose`
- `headline`
- `body`
- `fact_or_claim_ids`
- `asset_ids`
- `keyword_cluster_ids`
- `sku_scope`
- `validation_state`

FAQ 只能回答已有事实；未知答案进入 `seller_questions`。比较表必须使用相同口径，不能无证据点名或贬低竞品。

#### 步骤 5：Amazon A+ 分支

1. 从 A+ API 模型取得当前可用 Content Type、模块及字段限制；`maximum_module_count` 只是用户偏好，实际上限取其与当前 API/主体能力的更小值；
2. 根据内容任务选择文本、图片、技术规格、比较表等模块；
3. 校验每个 headline/body/alt text/图片的 Schema 和资产要求；
4. 生成完整 `ContentDocument` 预览，至少包含 `name`、`contentType`、可选 `contentSubType`、`locale`、`contentModuleList` 及模块专属嵌套字段；平台中立的 `DetailModuleV1` 只是编辑蓝图，不是提交体；
5. 以同一 `contentReferenceKey` 读取当前 ASIN relations；每次把响应的 `nextPageToken` 作为下一请求的 `pageToken`，直到响应 `nextPageToken` 缺失或为空，并保存抓取时间后，才能认定 current relation set 完整。不得把请求参数 `pageToken` 是否为空当作终止判断；分页中断、不完整或快照过期时禁止关系更新；
6. `postContentDocumentAsinRelations` 的语义是 **全量替换**，不是“追加这些 ASIN”。先把当前全集和期望全集去重、排序并计算集合哈希，再输出 `added` 与 `removed` 差集；目标全集遗漏的 ASIN 会被解除关联，其内容可能被暂停，因此只要 `removed` 非空就必须有明确移除审批；
7. 对“当前 ContentDocument hash + 期望 relation set hash”调用 `validateContentDocumentAsinRelations`。HTTP 200 只表示校验请求被执行；必须另存 `not_run/passed/failed/stale/unavailable` 状态、请求 ID 和时间。只有校验已运行、返回业务错误数组为空且校验绑定的两个哈希仍未变化，状态才是 `passed`；空 issue 数组不能自行代表“已通过”；
8. 只有关系快照完整且新鲜、ContentDocument 模型校验有效、关系校验 `passed`、集合差异可复算且所有移除已批准时，才输出 `ready_for_relation_update`；否则只输出审核或阻断状态；
9. 本节点不发布；后续节点不得把 `DRAFT/SUBMITTED` 当作 `APPROVED`，并按官方限频查询审批状态。

Amazon 官方 A+ 文档把内容表示为一个或多个内容模块，不同模块字段有各自长度与图片要求；这些限制从当前模型读取，ASIN 关系按官方管理流程单独维护。[Amazon A+ Content 模块示例](https://developer-docs.amazon.com/sp-api/lang-en_US/docs/a-plus-content-examples)、[Manage A+ Content](https://developer-docs.amazon.com/sp-api/docs/manage-aplus-content)

#### 步骤 6：TikTok Shop 描述分支

1. 从 Category Rules/Get Attributes 确定目标类目必需信息；
2. 生成短段落、卖点块、规格、使用/保养、包装和警示；
3. 渲染为有效 HTML，同时保留纯文本用于语义和长度校验；
4. 清理脚本、事件属性、外链、联系方式、二维码和站外引流；
5. 图片占位在发布前必须转换为 TikTok Shop 接受的资源地址；
6. 只做描述字段级 Schema、事实、声明与 HTML 校验；新品的 Check Product Listing 需要标题、属性、SKU 等完整请求，必须等节点 10 完成组装后调用；现有商品编辑改走当前 Edit/Partial Edit Schema 与提交/audit 路径。Product Information Issue Diagnosis 也不能用于验证未发布草稿。

TikTok Shop Product API 的描述字段支持 HTML，但平台会按原生页面渲染方式处理标签；实现仍应使用允许的安全子集和预览验证。跨境商品提交必须走当前 Product Management workflow 的实时 Schema，不能继续调用已经退役的 Global Product API。[TikTok Shop HTML 描述说明](https://partner.tiktokshop.com/docv2/page/html-tags-are-supported-in-product-descriptions)、[新 Product Management workflow](https://partner.tiktokshop.com/docv2/page/a5crrkzs)、[旧 Global Product 流程退役公告](https://partner.tiktokshop.com/docv2/page/fapus8ql)

#### 步骤 7：跨字段与事实校验

- 数字、单位、数量、材质、成分、型号、适配和包装逐项回查；
- 与标题、卖点、属性、图片 OCR 和变体保持一致；
- 检查否定关系、条件词和适用 SKU 未在长文中丢失；
- 检查 HTML/模块 Schema、链接、资产、字符和重复；
- 未通过字段不进入 payload preview。

## 15. 节点 15：多语言翻译与本地化

### 15.1 目的与边界

将已验证 Listing 内容转换为目标市场可理解、可搜索、事实不变的版本。该节点支持三种模式：

- `faithful_translation`：忠实翻译，不宣称 SEO 优化；
- `market_localization`：使用目标市场关键词资产重构表达；
- `qa_only`：只检查已有目标语言 Listing。

本地化不是逐字翻译。目标关键词必须重新取得或验证，不能把 Amazon US 的英文词量或 TikTok Shop US 推荐词直接翻译后当作另一市场的搜索证据。

### 15.2 输入

### 15.3 处理逻辑

#### 步骤 1：分段和保护实体

- 按标题 segment、卖点、详情模块、FAQ、Alt text、属性和值、变体标签拆分；
- 每段保留 `claim_ids`、事实路径、关键词链接和 HTML/模块位置；
- 锁定品牌、型号、GTIN、seller SKU、标准号、认证编号、变量占位和不可翻译专名；
- 保护数字与单位成对关系，禁止只翻数字周围文字后改变含义。

#### 步骤 2：术语与翻译记忆

1. 精确匹配已批准翻译；
2. 模糊匹配只作为候选，不自动覆盖；
3. 同一术语在不同类目/语境可有不同译法，按 target + category + locale 选择；
4. 多个同级术语冲突时进入人工复核；
5. 机器翻译不得改写人工锁定的 `LOCAL_OVERRIDE`。

#### 步骤 3：语义翻译

- 先用目标 rule bundle 逐条重评源 ClaimLedger 的 `support_status/allowed_target_ids/required_qualifiers/review_level/risk_codes`，生成新的目标 `effective_target_claim_ledger`；源账本只作 parent，不能直接当目标市场账本；
- 先翻译事实语义和限定条件，再调整语序与品牌语气；
- 保留否定、比较范围、使用条件、适用对象和 SKU scope；
- 监管、健康、安全、成分、认证和保证声明采用高风险路径；
- 不理解的源句返回 `unresolved`，不能用流畅但不同义的句子掩盖。

#### 步骤 4：市场本地化

- 将日期、数字格式、计量显示和标点调整到目标 locale；
- 单位转换必须使用确定性换算，保存原值、原单位、目标值、舍入规则和可逆关系；
- 服装/鞋码等非线性地区尺码使用版本化尺码表，不能简单乘除；
- 币价不属于纯文案本地化；只有用户明确提供价格/汇率策略时才生成显示建议，不修改 Offer；
- 调整文化表达和使用场景时不能新增商品用途或改变合规范围。

#### 步骤 5：目标市场 SEO 重建

`market_localization` 模式按目标 `KeywordAssetV1` 重新分配概念：

- 找到源内容中的 semantic concept；
- 选择目标市场有证据的 surface form；
- 重新执行标题/字段预算和重复校验；
- 源市场高优先级词在目标市场无证据时不强行保留；
- 目标市场新增词仍须通过商品事实和声明门禁。

#### 步骤 6：字段所有权与平台同步

对跨市场同步场景记录：

- `cross_market_inherited`
- `platform_auto_translated`
- `local_override`
- `locked`

Amazon Build International Listings 等工具可能自动尝试翻译和创建目标页面，仍需检查本地关键词与表达；Amazon 官方也建议针对目标受众进一步打磨机器翻译。[Amazon Listing 翻译指南](https://sell.amazon.com/blog/amazon-listing-translation)

TikTok Shop 跨市场商品同步时，应保留源商品与目标市场商品的字段所有权，避免后续更新覆盖当地人工内容。图片文字翻译若使用平台异步任务，要返回 task 状态而非同步成功。自 2026-01-31 起旧 Global Product Management flow 被逐步关闭并最终退役，所以执行器必须通过当前 Product Management workflow/capability 发现接口和覆盖语义，禁止生成 `Create/Edit/Partial Edit Global Product` 调用。[TikTok Shop 退役公告](https://partner.tiktokshop.com/docv2/page/fapus8ql)

- source/global 的 category/attribute/value ID 必须经官方映射到 target/local ID；只有 API 明确确认时才能复用原 ID，不得依赖“ID 跨市场不变”假设。
- 绑定 canonical `product_id + source_management_product_id + target_market_product_id + merchant/target authorization + source_hash + current_target_hash`；生成更新预览前重新比较 hash，本地覆盖变化则返回冲突。
- 更新方式只从当前 workflow Schema/capability 选择 `partial_update` 或 `full_update`。若当前操作是完整覆盖，只有 source/target 两份完整 API 快照已覆盖所有可能被改写的内容、属性、平台、本地 Offer/价格和 local overrides 时才可输出 `safe_for_automatic_update=true`；否则固定为 false 并只输出草稿。

#### 步骤 7：确定性 QA

逐段检查：

1. 品牌、型号、GTIN、SKU 和认证编号完全一致；
2. 所有数字、单位、数量、百分比和区间语义一致；
3. 否定词、条件、比较对象和适用范围未丢失；
4. 术语一致，HTML 标签和占位没有破坏；
5. 目标语言和 locale 正确；
6. 重新通过目标字段长度、字符、规则和声明校验；
7. source segment 与 target segment 的 claim 映射完整。

回译只是一项信号，不能替代数字、实体和事实的确定性比较。

#### 步骤 8：生成目标变更集与请求预览

1. 将本地化包与目标市场当前快照逐字段比较，生成 `add/replace/remove/preserve` diff；新品从空基线生成 add，老品必须绑定目标 `content_hash`；
2. 保留每项 diff 的 source segment、claim、keyword、术语、单位换算与审批引用，关键实体或高风险声明未决时不得映射 wire；
3. 按目标平台当前 Schema 把已批准 diff 映射为请求 operation，并生成 body artifact 与包含 identity/endpoint/method/body hash 的 request-envelope artifact；逐项证明没有额外字段；
4. Amazon 使用目标 marketplace 的 PTD 与 Listings Items/A+ 分支；TikTok Shop 新品使用 Create Product + Check Product Listing，老品使用当前 Edit/Partial Edit workflow 并等待后续 audit/webhook；
5. `qa_only` 只输出问题和建议，不生成 payload；跨市场 update capability、完整覆盖域、目标商品身份或并发基线不确定时仅输出 `draft_only`；
6. `ready_for_review` 只表示请求预览可供人工审核，发布和平台审核仍由后续节点执行。

## 16. 节点 16：规格名称与变体文案优化

### 16.1 目的与边界

在不改变变体事实和库存身份的前提下，标准化、翻译和缩短消费者可见的规格轴与规格值。输入必须来自第一阶段“SKU／变体结构重建”的标准结构，不能再次从标题猜测变体。

该节点绝不自动修改平台 SKU ID、seller SKU、GTIN、价格、库存或真实组合。`copy_ready=true` 只代表文案映射完成，不代表商品可发布。

### 16.2 输入

| 变量名 | 类型 | 必选 | 说明 |
| --- | --- | ---: | --- |
| `product_snapshot` | `object` | 是 | 不可变商品及标准变体事实快照 |
| `variant_builder_artifact` | `object` | 是 | 第一阶段节点 4 输出封装；`output` 为原始 `VariantBuilderOutputV1`，hash 覆盖规范轴、SKU、平台结构、报告、问题和 readiness |
| `target` | `object` | 是 | 平台、市场、locale 和目标类目/商品类型 |
| `rule_bundle_ref` | `string` | 是 | 变体主题/Sales Attributes、枚举、长度和自定义值能力 |
| `current_variant_copy` | `list<object>` | 否 | 当前轴名、值名和平台 ID |
| `terminology` | `list<object>` | 否 | 颜色、尺寸、材质、容量、数量等受控词典 |
| `keyword_asset` | `object` | 否 | 仅用于术语一致性，不允许变体标签 SEO 堆词 |
| `optimization_brief` | `object` | 否 | 人工确认后的可编辑轴/值、目标 issue、锁定项和改动预算 |
| `variant_copy_config` | `object` | 是 | 单位显示、缩短、碰撞消歧、人工锁定和未知值策略 |

### 16.3 处理逻辑

#### 步骤 1：身份与显示层分离

```text
identity layer: product_id / platform_product_id / sku_id / seller_sku / GTIN
semantic layer: canonical axis / canonical value / measurement
display layer: localized axis name / localized value / combined SKU label
```

只允许修改 display layer。任何生成建议都必须能反向映射到原始规范值。

#### 步骤 2：读取平台 Schema

**Amazon：** 根据完整 PTD 的 `parentageLevel`、variation theme、`allOf` 条件和枚举建立映射。确定性门禁包括：CHILD 必须有 `parent_sku`；父子必须使用同一 theme；theme 对应轴的条件必填项全部存在；新建 Listing 不得选用 `$lifecycle.enumDeprecated` 的 theme。同一家族还必须保持相同品牌、核心商品类型和功能；评论共享资格是独立政策结果，不从本节点 `family_integrity` 推导。[Amazon PTD parentageLevel 指南](https://developer-docs.amazon.com/sp-api/lang-en_EN/docs/retrieve-a-product-type-definition)、[Amazon Variation Listing 指南](https://sell.amazon.com/blog/amazon-variation-listing)

**TikTok Shop：** 从目标叶子类目 Get Attributes 取得 Product Attributes 与 Sales Attributes；anchor product 连接同一商品的各 SKU，颜色、尺寸、长度等 Sales Attributes 定义 SKU 差异，整件商品共享属性不能错误变成变体轴。[TikTok Shop Get Attributes](https://partner.tiktokshop.com/docv2/page/get-attributes-202309)

#### 步骤 3：轴和值规范化

- 将供应商别名映射到平台轴，如 colour/color → 颜色概念；
- 区分产品尺寸、包装尺寸、服装尺码、容量和件数；
- 受控枚举优先使用平台 ID/value ID；只有 Schema 允许时才生成自定义显示值；
- 颜色、材质等不能仅凭图片模型自动确定为最终事实；
- 数值单位转换保留原值并使用统一舍入策略；
- 套装数量要与实际包装结构一致。

#### 步骤 4：本地化显示值

- 使用目标 locale 术语，不把英语 Title Case 强加给所有语言；
- 保留品牌色或型号色的批准写法；
- 缩短时优先删除冗余供应商编码、重复轴名和非区分信息；
- 不增加核心关键词、促销、库存或“热卖”信息；
- 合并标签的顺序来自类目/locale 规则，如“颜色 · 尺寸”，不是固定英文顺序。

#### 步骤 5：碰撞和唯一性

对显示值执行 Unicode case-fold、标点/空白、locale collation 和单位归一后检查：

1. 同一轴的两个规范值是否变成相同显示值；
2. 两个 SKU 的完整属性组合是否相同；
3. 不同原值是否因翻译、缩写或舍入碰撞；
4. 仅大小写或全半角差异是否造成消费者无法区分；
5. 媒体与规格值的关联是否仍唯一。

出现碰撞时仅增加最小必要限定，如材质、精确单位或型号；不得为了消歧创造不存在的差异。仍不能区分则进入人工复核。

#### 步骤 6：组合完整性

- 每个 SKU 恰好对应一个允许的属性组合；
- 每个组合最多一个真实 SKU；
- 第一阶段 `canonical_skus.state=quarantined` 的记录只输出复核任务，不生成可应用变体文案；
- 稀疏矩阵不自动补出不存在的 SKU；
- planned SKU 只能保留 planned 状态，不伪造库存；
- 父体标题不枚举全部颜色/尺码；子体标题按当前政策保留最重要的该 SKU 变体属性，完整轴值仍保留在变体显示层；
- TikTok Shop 所有 SKU 必须使用相同的 Sales Attribute ID 集合和数量，且每个属性在单个 SKU 中只能出现一次；不满足时 `copy_ready=false`；
- 所有 ID、库存和价格关联在优化前后完全一致。

#### 步骤 7：稳定性与可逆性

相同规范输入、locale、词典和规则版本必须生成相同显示名。输出 source→canonical→platform→display 全链路和变更日志，确保可以回滚或重新本地化。

### 16.5 业务结果与错误码

| 代码 | 分类 | 默认处理 |
| --- | --- | --- |
| `VARIANT_COPY_NO_CHANGE` | 业务结果 | 正常返回现有映射 |
| `VARIANT_COPY_CUSTOM_VALUE_UNSUPPORTED` | 复核 | 保留候选，不生成平台 patch |
| `VARIANT_COPY_DISPLAY_COLLISION` | 复核 | 自动消歧失败时隔离相关 SKU |
| `VARIANT_COPY_COMBINATION_CONFLICT` | 复核/阻断 | 不改变真实组合 |
| `VARIANT_COPY_PARENT_LINK_OR_THEME_INVALID` | 阻断 | Amazon 父链、theme 一致性、条件轴或 deprecated theme 不通过时 `copy_ready=false` |
| `VARIANT_COPY_SALES_ATTRIBUTE_SET_INVALID` | 阻断 | TikTok Shop SKU 销售属性集合/数量不一致或单 SKU 属性重复时 `copy_ready=false` |
| `VARIANT_COPY_IDENTITY_CHANGED` | 阻断 | 丢弃修改并报告 |
| `VARIANT_COPY_INPUT_INVALID` | 致命 | 不重试 |
| `VARIANT_COPY_SCHEMA_UNAVAILABLE` | 致命 | 无允许缓存时中断 |
| `VARIANT_COPY_OUTPUT_INVALID` | 致命 | 不返回不可逆映射 |
