## 场景及次数

沿现有客户端→Native→Host→Codex Runtime→MCP/Broker→worker链，在普通空白对话使用`kimi-k3.1-pro` / `kimi-k3-1-pro-max-v1`，自动复用客户端现有Kimi Key，不单独配置连接器。不加载专家、附件或技能。权限保持“请求批准”。

唯一用户消息：先用`kimi_web_search`查询“IANA example domains”，limit=3，展示标题、URL和摘要；再用`kimi_web_fetch`读取`https://www.iana.org/help/example-domains`；依据正文，用不超过150字说明example.com/example.org的用途及能否注册或转让，并附来源。每项只一次，失败停止。

| 项目 | 新授权拟定上限 | 约束 |
|---|---:|---|
| 用户发送 | 1条 | 不追加“继续” |
| K3.1 Pro模型HTTP | 3次 | 初始请求与工具后续推理共用总额；发现、压缩或辅助请求也计数 |
| Search Basic | 1次 | 仅上述query/limit，UI批准一次 |
| Fetch | 1次 | 仅上述URL，UI批准一次 |
| 重试 | 0次 | 失败、超时、截断、用量未知均停止 |
| 其它收费入口/原生搜索/估算token/余额/models | 0次 | 验收入口约束；不改产品默认能力 |

若模型合并工具请求，按实际更少的模型次数计账，不补足3次；若3次内未完成，记未通过，不增加请求。拒绝后零HTTP先用本地普通预检确认，不额外消费一次模型请求来生成拒绝场景。重复工具提案不批准，关闭后续模型转发。

## 通过标准与边界

1. 新构建来源、K3.1身份、Host专家资源摘要和worker一致；本地拒绝后模型/Search/Fetch全部0请求。
2. 客户端显示Kimi连接器可用，无再次填Key或启用步骤。真实UI审批、MCP调用与供应商发送能关联到本条对话。
3. Search返回1–3条相关标题、HTTP(S) URL及非空摘要；Fetch返回指定网页非空标题和正文，包含示例域名用途及不可注册/转让事实。不能以HTTP200代替内容检查。
4. 后续模型输入实际包含两项工具结果，短答正确且带IANA链接；UI两项工具完成、回答正常结束。
5. 正常退出并同构建重开，只读历史，工具记录和答案保留，零新增请求。服务按正常流程清理；不能安全退出则停手报告。
6. 报告模型实际发送次数/usage、Search/Fetch实际发送与成功次数、金额核算、审批和重开结果。一次失败即停止，不重试/换Key/换题/充值。
