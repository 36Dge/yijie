## 第一轮事实

仅构建 20261030-01 一次，6 分 45 秒；首次填充隔离缓存，保留 08、09 及旧证据。真实 App：E2 Pro、E3 Fetch、E4 Basic 正文、E5 Basic 摘要→用户第二回合 Fetch 均成功且回答可见。E1 首次提议 Pro 而非 Basic，随后审批超时，未发送工具请求；E6 正确提议 Pro，但准备起算的 60 秒截止已无完整 35 秒执行预算，工具未进入审批。两项不能计 PASS，E7 尚未运行。每例不核对质量、来源关系、费用记录。

## 续跑前审计

观察器另有请求衔接缺陷：Runtime 可在收到终态 SSE 后、上游 HTTP EOF 之前发出下一模型请求，旧观察器将仍在收尾的请求视作并发而永久停止。第一轮 request_rejected 与最后一条 terminal 已到但 stream_complete=false 相符；具体异常分支未单独记载，因此这是代码与时序支持的根因判断，不冒称有完整逐请求诊断。修复为本地条件等待前一响应收尾，再重验软停止并预占；不并发发送、不自动重试、不改模型输入输出，不授工具批准。

加入正常关闭的 Alpha 观察记录续接：新文件固定上一文件摘要，累计既有模型估算、请求数及工具预留；原记录不改、不复位 20 元阈值。contract-impact=none，仅本地验收观察器，不改产品 wire、审批或 Runtime。标准模式保持原样。

E6 的 prepare+60 秒规则是 24 号及 Contracts 0.3 候选的既有保守规则，不能擅自将它改为延长批准。此次按原场景显式重开复验 E1/E6，执行 E7；已过四例不重复。原失败仍保留。若仍无法成功，维持未关闭而继续诊断。

续跑只进行这项有明确缺陷依据的修复；需要新来源制品时复用同一缓存并产生新 generation，绝不覆盖已有 App。
