## 目标与范围

在易界客户端普通新对话中，证明模型能选择Kimi Search/Fetch，经现有Native→Host→Codex Runtime→MCP/Broker→产品worker调用，收到真实结果后作答，并在正常重开后保留工具记录和答案。继续自动复用现有Kimi模型Key，不填写、复制保存或展示Key。

保持当前kimi-k3及既有推理配置，真实用户输入仅1条。推荐顺序执行Search→Fetch→回答，模型HTTP最多3次；若原生机制合并工具请求，按实际更少次数记账，不补足次数。每次工具后的模型续推理、发现工具、压缩、辅助生成等若需要上游模型HTTP，均占用同一总额，不能另算免费。到上限仍未完成则本轮不通过。

本轮是带明确token预算的真实客户端验收，不声称与未设输出上限的日常请求逐字节相同。保持原生Agent循环与Codex内核，不新增业务调用编排器，不直接curl替代客户端。contract-impact=none：当前只新增方案文档；拟补的计量边界限于本地验收入口，不变更公开协议、产品持久化或审批语义。若后续需要产品契约变更，先重新评估。

## 固定场景与次数

在普通空白对话中选用现有Kimi连接器，不加载专家、技能或附件，使用“请求批准”模式。仅在本次验收配置中限制其他联网工具入口，保留产品日常原生搜索能力。不能只用提示词保证不会额外收费，发送前必须确认有效限制。

固定用户消息：

> 请仅使用已选的Kimi连接器完成这次验证：先调用kimi_web_search，query为“IANA example domains”，limit为3，展示返回的标题、URL和摘要。收到结果后调用kimi_web_fetch，读取https://www.iana.org/help/example-domains。最后根据抓取正文，用不超过150字说明example.com/example.org的用途及能否注册或转让，并附来源链接。Search和Fetch各只能调用一次；任一步失败就停止，不重试、不调用其他联网工具、不执行终端命令。

| 项目 | 本轮额度 | 计数依据 |
|---|---:|---|
| 用户发送消息 | 1条 | 客户端新对话，不追加“继续” |
| Kimi模型推理HTTP | 最多3次 | 每次实际向/v1/responses发送均记账，包含续推理及失败尝试 |
| Search Basic | 最多1次 | 产品worker的实际HTTP发送，query固定、limit=3 |
| Fetch | 最多1次 | 产品worker的实际HTTP发送，固定IANA URL |
| 模型/工具重试 | 0次 | 超时或结果未知也不补发 |
| 原生搜索、Search Pro、其他收费工具、图像、/models、余额接口 | 0次 | 不借用其他任务额度 |
| 远程token估算接口 | 0次 | 本方案不包含额外账户接口请求 |

本地initialize/list、准备连接器和历史只读不计为模型调用，但须确认它们没有暗中触发上游HTTP。先复核正常拒绝零供应商发送的本地预检；13报告已有真实拒绝证据，本轮不额外消费模型额度去诱导一次拒绝。真实UI只批准与上述参数一致的Search和Fetch各一次，不批准重复提案。

## 费用上限与发送前约束

申请本轮总预算上限 **人民币5.00元**，包括所有模型输入、思考/输出、缓存和两项工具费用。不是预计必须消费5元，也不是上一轮0.02元预算的续用。

2026-10-24核对官方[Kimi模型价格入口](https://platform.kimi.com/)及[缓存计费说明](https://platform.kimi.com/docs/guide/context-caching)：kimi-k3输入未命中20元/百万token，缓存写入5m为20元、1h为40元，缓存读取2元；输出100元/百万token。输入的未缓存、缓存读和缓存写为互斥分类，不重复相加。按最贵输入分类40元/百万token保守预留。Search Basic和Fetch按[官方工具定价](https://platform.kimi.com/docs/pricing/websearch)各0.01元/成功次。

拟定每次请求的完整输入上界20000 tokens，包括系统指令、工具定义、历史、思考回传和工具结果；请求max_output_tokens不高于8192，包括思考及答案。既有FEAT-163证据中曾出现供应商报告8195输出，因此费用预留按8288而非恰好8192计算，原始usage不抹平。

保守预留计算：3 × (20000 × 40 + 8288 × 100) / 1000000 + 0.02 = **4.9064元**，其余0.0936元留在5元预算内。预计实际用量通常低于这个预留，但当前不把预计用量当硬上界；供应商最终账单未查询时，只报告usage及公开单价核算。

**尚待完成的零费用前置门禁**：现有chat-model-smoke-meter.py已有总HTTP次数和8192输出限制，但缺完整输入token上界与人民币费用预留，不能直接声称已保证5元上限。确认后先在该既有验收入口补齐并离线验证：

1. 使用独立一次性台账，在发送前持久化占用额度，拒绝第4次模型请求；首个失败/不完整/用量不明后关闭后续发送，无重试。
2. 通过可核验的Kimi兼容本地计数或有依据的保守上界验证完整输入不超过20000；不能用字符数除以4、其他模型tokenizer或上轮usage猜算。若做不到，停止于零收费阶段，不以“结束后再算”替代发送前限制，不擅自增加远程估算接口。
3. 检查输出限制及最坏费用预留，保守计入缓存1h单价。价格变化、隐藏上下文/不可计数内容、其他付费入口无法关闭或任一预算无法约束，均不发送。剩余额度不足也不自动压缩或另起回合。
4. 使用既有canonical本地verification base URL与标准构建入口，响应原样转发，仅公开记录验收输出上限设置等必要差异；不修改/伪装可执行文件，不替换Runtime/worker、不截断或伪造供应商结果。
5. 核对本次工具单次批准及worker无重试，重复提案拒绝且关闭后续模型发送。真实审批仍由产品界面和原有Broker执行，计量脚本不代替审批引擎。

上述门禁是执行条件，不是已经实现的能力。本轮确认授权可以覆盖这项零费用验收入口补齐；在门禁通过前不能发送收费请求。若需改变上述模型、次数、token或金额范围，先报告原因并取得新确认。

## 执行顺序与通过标准

1. 记录当前源码/构建来源，核对Host专家摘要、worker来源及正常服务就绪；保护FEAT-163现有改动。零费用门禁失败立即停止，不把启动成功当对话成功。
2. 正常打开客户端，新建普通对话，选用Kimi连接器，确认无需重新填写或启用；发送上述唯一消息。
3. 在真实UI逐项核对并批准Search/Fetch。模型工具名、参数、审批身份、MCP call及供应商发送记录必须关联到这条对话；不能用旧结果顶替。
4. Search成功返回1–3条相关结果，每条title/url/snippet完整，至少有可用的非空标题/摘要及HTTP(S) URL；Fetch返回指定URL的非空标题、正文，包含示例域名的文档用途及不可注册/转让事实。空结果、错误页、协议/解析失败不能记通过。
5. 后继模型请求实际包含对应工具结果；最终短答准确使用正文并附IANA来源。UI显示两项真实工具状态和结果，最终消息完整结束，不能仅凭HTTP200判PASS。
6. 正常Cmd-Q后按同构建正常重开，仅查看已保存历史；两项工具记录及答案保留，无新增模型/工具请求。结束后按canonical入口恢复日常无验收代理配置，正常停止计量进程；不发送额外验证消息。
7. 提交结果表：实际用户回合、模型HTTP/usage、Search/Fetch发送与成功次数、审批、耗时、费用核算、历史保持和未执行项。用量缺失记unknown，不写0。成功仅覆盖此最小端到端场景，不自动将整个FEAT-162 D4或FEAT-163标PASS。
