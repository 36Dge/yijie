## 1. 用户结果与范围

在一个kimi-web连接器内提供kimi_web_search（Basic）、kimi_web_search_pro（Pro）、kimi_web_fetch（Fetch）。沿用现有K3.1 Pro及模型Key自动复用，安装/本地准备不发供应商请求，不要求重复填Key或单独启用。当前会话选用、停用/卸载与原ask逐次审批保持。无需Basic/Pro手动切换或单独激活技能。

目录仍61项、容量62、单轮连接器选择上限58；增加第三个工具不增加目录项。保留K3.1模型身份、旧K3退役状态、原数据与迁移、专家资源；原生搜索按§12条件保留。非目标：原始HTML、无头浏览器、JS渲染控制、登录态网页、知识库入库、向量数据库、批量爬虫、定时任务扩权、新Agent循环、额外分类模型调用、Runtime核心修改、生产发布。

## 2. 模型选择规则

规则仅在当前任务允许联网且kimi-web已选、可用时生效。执行优先级：用户明确约束→结果所需能力→默认规则。工具是否存在和选择正确性不得用prompt替代Host/Broker权限校验。

| 任务意图 | 选择与参数 | 停止/补充条件 |
|---|---|---|
| 展示网页列表、标题、摘要、链接、找官网 | Basic，include_content=false | 结果足够即结束，不再为同一需求调用Pro或原生搜索 |
| 采集搜索到的可提取正文供用户自行加工 | Basic，include_content=true | 不承诺完整页面；缺正文/截断明确标识，不自动入库 |
| 联网问答、事实核查、RAG材料、研究/报告/总结 | Pro | 直接取相关chunks，不先做一次Basic试探 |
| 限定来源站点或时间 | Pro，sites/time_window | 不静默丢弃用户约束；结果不足说明证据不足 |
| 读取/总结用户给定URL的内容 | Fetch | URL只是举例、来源线索或用于找类似页面时，仍按实际任务选搜索 |
| 限站点/时间并要求某页完整可提取正文 | Pro找来源，再按需Fetch | 每次单独审批计数；只取必要页面，不批量默认抓全部结果 |
| 明确不联网、仅用附件/已有材料、未选连接器 | 不调用本连接器 | 不补造来源，不偷偷切其他接口 |

用户明确只用Basic但又要求Pro专属约束时，说明能力冲突；不擅自换接口，也不把查询词中的site/时间文字冒充结构化过滤。模糊问题默认采用任务交付形式，只有无法合理确定实体、范围或互斥约束时才澄清。

普通对话运行规则以Contracts生成的三个tool description为入口。删除旧Basic描述中“一般联网回答可使用原生搜索”的冲突引导：当kimi-web已选且任务为问答时优先Pro；未选时不更改既有原生搜索策略。不得在Host新建关键词路由器、规划器或第二个模型回合，模型仍沿原function/tool calling选择工具。 Host通用运行指令须尊重当前已选且适用的检索连接器，不能同时无条件要求原生搜索；未选kimi-web时保留原生默认；有效选中且为K3.1时统一在正常Host配置关闭hosted搜索，不按prompt再次判断适用性。无需联网的提问仍可直接回答。此层只解决平台选集优先级，三工具分工仍唯一来自同源tool description。

查询词由当前对话模型生成，Connectors按批准值原样映射为text_query，不偷偷改写。用实体、时间、限定角度形成一个信息需求；合并同需求追问，不拼接互不相关问题。结果不足时补实体、时间、角度或语言；不进行同义反复搜索。模型不得凭空指定用户没有要求的站点限制。

## 3. 源契约与输入输出

权威源为Contracts `compatibility/web-retrieval/{wire.schema.json,tools.json}`及对应generator。当前web-retrieval/1@0.2.0；计划以新本地候选0.3.0扩展，不声称已发布版本。所有新增常量、schema、描述、预算和错误由源生成，不手改SDK/consumer快照。原0.2.0保留作明确兼容基线。

| 工具 | 输入 | 固定上游 | 成功结果 |
|---|---|---|---|
| kimi_web_search | query（原非空/2048字符约束）、limit默认5/1–20、include_content可选布尔默认false | POST /v1/tools/search，text_query=query | 默认保留原results/title/url/snippet/truncated；正文模式每项增加text/content_status，顶层增加dropped_results |
| kimi_web_search_pro | query、limit同Basic；sites可选最多5项；time_window可选 | POST /v1/tools/search_pro | results含title/url/snippet/site_name/date/authority/chunks/content_status，顶层truncated/dropped_results |
| kimi_web_fetch | 原公开URL参数 | POST /v1/tools/fetch | 原url/title/markdown/truncated，不增加新格式 |

Basic旧请求（省略include_content或false）必须保持旧响应结构、归一化/错误行为及按剩余时间执行的语义，不加入text、content_status或dropped_results。include_content=true时每项text为提取文本，缺失时为空字符串；不将该text称为HTML或保证完整全文。新输出schema按请求模式约束字段，旧消费者不发送新字段、不接收新模式；新模式的逐页过滤不能通过共用函数悄悄改变默认Basic。

Pro chunks按网页归属保留，每项为text和有限数值score；保留供应商顺序。authority、date、site_name等缺失字符串按官方空串语义处理；不编造值或把无效类型强转成可信内容。score只在同次查询内有相对意义，authority不设未经官方确认的可信阈值。模型回答必须引用关联的真实URL，不能把MCP结果伪造成原生web_search sources。新增模式的逐页状态、无效页和裁剪语义固定如下，均须先进入权威schema及生成器：

| 字段/条件 | 确定语义 |
|---|---|
| content_status=available | 上游至少有一段非空白正文且正文未被本地裁剪/删片段；仅指本次提取材料可用，不表示完整网页 |
| content_status=unavailable | 上游没有可用正文：Basic缺text或空白text；Pro缺chunks、空数组或全部为合法空白片段 |
| content_status=truncated | 上游原有正文而本地裁剪文本或删除chunk，即使最终为空也保持truncated，不变为unavailable |
| dropped_results | 新模式必填非负整数，原始search_results项数减最终results项数；同一页只计一次，包含无效页、超出limit及预算丢页；不计上游未返回的页 |
| 顶层truncated | 任一页未交付、任一正文/标题/摘要被本地裁剪即为true；无丢页/裁剪为false。缺正文本身不置true；不额外增加含义重复的page.truncated或partial布尔 |

UI按每页content_status分别显示“正文可用/未取得正文/正文已截断”，按dropped_results显示未交付页数；顶层truncated提示整体材料不完整。正文状态在裁剪前确定来源事实，裁剪后更新，不得只凭最后text/chunks是否为空推导。标题/摘要裁剪仅置顶层truncated，不误称该页正文被裁剪。

只对新Basic正文/Pro执行以下归一化：search_results必须为数组，否则invalid_response；每项必须为对象，url必须是沿用原public_url规则接受的原始公开URL，缺失/空白/不接受的URL使该页无效，不补造、不改写、不截短。title/snippet及Pro元数据字符串缺失归空串，非字符串（包括null）使该页无效；空标题允许UI以真实URL作为展示标签，不伪造标题。Basic缺text归空串，非字符串使该页无效；Pro缺chunks归空数组，非数组（包括null）或任一chunk非对象、text非字符串/缺失、score缺失/非有限数值使该页无效，不把坏字段强转成正文。未知供应商字段忽略，不进入输出或日志。

逐项舍弃无效页，保留有效页及片段的供应商顺序，再按limit和总字节预算裁剪。不把一页无效传播为整单失败；至少一页保留即成功但明确丢页。原始空数组返回成功空结果、dropped_results=0、truncated=false；原始非空却全部结构/来源无效返回invalid_response；存在合法页但无法交付至少一页必要来源元数据返回response_too_large，不能伪装成成功空结果。费用始终依据过滤前事实，见§6。

sites遵守官方非空、无空白/括号、最多5项及本地总参数大小约束，多个站点按OR；不替用户扩展站点范围。time_window校验YYYY、YYYY-MM、YYYY-MM-DD及真实日历值，按周期首日比较start≤end。相对日期按任务当前时间和用户时区解释，尽量发送明确日期；不得将end=YYYY-MM误解为月末。任一不合法约束在发送前返回invalid_arguments，不静默删去后发出。

## 4. 兼容影响和激活顺序

产品扩展暂按contract-impact=breaking保守管理：新增工具资格集合、Basic可选正文结果和执行预算会影响跨仓消费者；仅有两工具硬编码断言不是已经证实wire破坏的全部依据。实施时验证旧请求→新provider、新响应→新reader、旧历史→新reader、旧provider遇新客户端的关闭路径，不把generate成功当成兼容证明。

先形成源契约及本地精确提交，生成并验证新reader/backend；再同步Host、Desktop及必要资源来源，最后以匹配的工具schema digest/安装资格快照激活三工具。旧Basic/Fetch入口双轨保留，旧版本不接收Pro或正文新模式；不得把新能力投影到旧工具资格中。既有两工具允许集合/生成器断言应按新版本明确演进，并保留旧版本用例。

新消费者未就绪时不激活；当前reader不能接受扩展时使用兼容reader，不手改hash或删除门禁。没有新数据库表/数据迁移；MCP原始内容沿现有加密历史保存。新增结果的展示、历史解码必须验证，不通过改写旧记录适配。除web-retrieval外，§5新增模式的审批/执行双截止投影涉及market broker/market-host审批契约，须登记相应源、生成物与Host/Desktop消费者；旧模式和旧审批记录保留原截止解释，不私自改同名旧字段含义。

## 5. 超时和权限期限

| 模式 | 上游timeout_seconds | 本地HTTP总上限 |
|---|---:|---:|
| Basic摘要 | 10 | 15秒 |
| Basic正文 | 30 | 35秒 |
| Pro | 30 | 35秒 |
| Fetch | 不新增上游超时参数 | 保持15秒 |

这些是有限产品策略，不向模型暴露任意超时或base URL。审批窗口仍最多60秒，租约仍受原300秒及Native scope限制；审批等待消耗原调用期限。首期保留Host工具等待60秒，不在批准后追加执行时间、不改变全局权限TTL。

默认Basic/Fetch维持旧规则：未过原批准/执行截止时，HTTP总上限为min(实际剩余时间,15秒)；不新加“必须剩余15秒”的门槛，上游参数保持原值。例：第50秒批准且剩10秒，允许在10秒上限内执行，5秒正常返回可成功。原截止已到、撤权或取消仍零HTTP拒绝。

只有Basic正文/Pro启用完整35秒预算规则。定义执行绝对截止D=min(原call截止,lease截止,Native scope截止,可信的外层MCP截止)，投递预留M=2秒，最晚批准截止A=D−35秒−M；M只预留Host/worker传递时间，不是保证任何调度都及时。无前置耗时且D距提案60秒时，可批准窗口至多约23秒；前置bind/排队/作用域到期会缩短，不向用户承诺固定23秒。

源契约为新模式明确decision_expires_at=A与execution_expires_at=D及模式预算。Host投影、Desktop倒计时/按钮、Broker裁决使用同一A；旧模式/旧reader保留原字段语义，新双截止仅对匹配新资格的消费者启用。A只约束Pending→Approved：在权威裁决时now<A才可批准，等于或超过A拒绝；已及时批准的调用不会在A到时被refresh/定时器改为Expired，后续仍受D、撤权、取消和一次消费约束。若A已到则不展示可批准卡片，直接明确“执行时间不足，请重新发起”；不伪造批准。

实际POST前在串行执行点再次核对批准参数/资格/取消、D及实际剩余时间；新模式不足35秒时零HTTP返回明确timeout/执行期限不足，恰好35秒可发送并由D硬约束HTTP全生命周期。不得降低30秒上游参数、自动续批/重放。UI退出loading并保留查询，用户可重新发起新调用；本地按钮禁用不替代服务端权威检查。

MCP绝对截止不能用worker接收时刻+60秒猜测：实施须从固定Runtime/Host调用链证明真实起点，沿既有边界传递可信预算或经验证的保守下界，计入bind/排队与IPC耗时。不能取得可信边界则新35秒模式禁止激活，旧模式不因此改变；不通过Runtime补丁或扩大TTL绕过。零费用时间值验证必须覆盖A前/等于/后、批准后越A但未越D、投递迟延使剩余不足35秒、较短lease/scope/MCP及旧模式晚批准；真实正常时序仍须E2/E4/E6/E7验证。

## 6. 结果大小、失败与费用

原始HTTP响应最多1MiB，超限明确response_too_large；整个CallToolResult最终序列化（含text、structuredContent、外层字段、转义和新增状态/计数）不超过65536字节，text中的JSON与structuredContent语义相等。不得裁断JSON后解析。新模式保留来源关系及供应商顺序，必要时裁剪文本/尾部片段或尾部结果；UTF-8边界安全，不截短URL、不编造摘要；每次变更均更新content_status/dropped_results/truncated再序列化核验。允许正文被裁至空但保留truncated状态；至少保留一页必要来源元数据，否则response_too_large。默认Basic和Fetch继续原裁剪规则，不借新字段改变旧输出，不承诺完整网页。

原始空列表是成功无结果；上游缺正文、部分页舍弃、本地正文截断和整单失败按§3区分，最终空正文不能一律叫“未取得正文”。模型可基于摘要回答有边界的问题或说明证据不足，必要时提出另一个获批来源读取。HTTP失败、工具isError、Runtime文本错误、不完整模型终态与未知usage分别记录；没有成功结果不能进入“检索完成”的产品状态。

固定同一Kimi API主机和三个白名单路径、同一既有模型Key快照；不向目标网页发送Key，不追加账户探测。保持无自动重试、无重定向、一次批准一次请求。错误不自动Basic/Pro互换；仅成功后发现新的证据需求才允许模型提出新的、仍须批准的调用。

预算沿已记录REST单价Basic0.01、Pro0.015、Fetch0.01元计算，执行授权前复核当时价格。搜索HTTP200且原始search_results非空即可能收费，即使chunks为空、全部页被过滤、客户端截断或本地归一化失败也不能记免费；解析/超限导致无法确认原始事实时费用保持未知预占。Fetch以成功且非空白markdown判据区分。超时/断开、模型失败无usage继续预占，不依据本地取消宣称免费。模型Token及原生web_search费用独立，完整费用准入见§9。

正常产品保留现有审批/费用提示；验收计量器扩展三工具、逐用例/会话/调用ID、三种正文状态、费用和模型次数。计量器只能观察、预占、准入和停止，不裁减真实工具集合、不改prompt/结果/输出限制，不扩成Agent或计费平台。日志仅存固定错误类别、数量/字节、耗时、摘要及受限request ID；不记录Key、完整查询/正文、任意响应头或供应商错误文本。限流可保留受限数值头，不后台重试。

## 7. 客户端主流程及所有状态

主流程：canonical实际客户端启动→已有Key本地准备→用户当前会话选用kimi-web→普通用户任务→模型依工具描述选择→原审批展示Basic/Pro/Fetch及完整参数→一次执行→MCP结果回灌→带真实来源的回答→正常重开历史。

继续使用原连接器选择器、审批卡片与工具详情；不新增独立模式设置页。卡片区分三工具，Pro显示站点/时间，Basic显示是否请求正文；结果详情可展开文本/片段与来源，截断和缺正文可见。保持原亮暗主题、键盘焦点和1180×760最小布局，不能靠改变系统外观制造验收环境。

| 状态 | 用户可观察行为 |
|---|---|
| idle | 已有模型Key自动准备；缺Key显示统一配置缺失；显式停用/卸载保持 |
| loading | 显示实际模型/等待审批/工具执行阶段，防重复提交；不伪造研究进度 |
| success | 展示真实结果和来源，工具成功与整轮回答完成分开 |
