## 3. 契约、归属与兼容

本轮文档 `contract-impact=none`。未来 4C-1 按 **breaking 保守审查**：执行准入收紧会影响已有候选写操作和存量队列可派发性，不能仅按新增按钮或 JSON 未变评为 none/additive；新增只读查询本身 additive。先形成 Desktop 私有候选准入/失败语义，再生成和接线。旧的只读用途、草案、管理及普通聊天合法路径保持；旧候选数据可读，不以“之前 capability 未开放”掩盖语义差异。

- Desktop 私有 IPC schema 是新查询封套的唯一源。按操作种类和原 request_id 查询当前 scope 下的 grant/manual 事实，返回“已观察/未观察”，已观察结果复用原 GrantView、准备回执/运行与绑定类型；不手写影子 DTO，不泄漏其它 scope。
- grant 已确认但 manual 未观察：明确“授权已保存，尚未确认运行受理”。manual 已观察：查回原 run、原操作及当前事实；不存在记录不能推定先前未执行，UI 不自动构造新 ID。
- 不新增公共 Host API、Runtime 方法、依赖或执行器。现有共享 payload 及精确 Runtime/Host 来源继续验证。若实施证据表明必须修改跨仓 wire，先回到相应唯一源评审，不临时在 Host/Desktop 复制字段。
- **普通 SQL15/Store5、候选 SQL23/Store6 不变，不预设 SQL24。** 两类回执查询已有表；行动许可为当前原生生命周期内状态，不伪装成长期授权。旧迁移、旧聊天和旧 unknown 历史不改写。回退先关闭新请求/claim并正常停止受管进程，再使用兼容23/6的只读、禁发候选；不降级写库、不删表、不恢复数据库副本覆盖现状。
- 预期代码范围为 Desktop，以及普通 Ask/计数资格证明所需的 Host 定向检查或最小适配；Contracts/Runtime 先只读复用。Host 若有必要修改，审查具体差异后更新精确候选来源锁，不放宽 dirty/floating 校验。

## 4. 有限确认与发送边界

推荐本批只对**当前暂停计划**开放“立即运行”，一次确认固定 `max_runs=1`，从原生确认时刻起最长 **10 分钟**有效；页面展示实际截止时间。现有契约可承载，不引入长期授权编辑器。计划 ID、revision、definition/workspace、当前 native authorization revision 均由原生校验。10 分钟是本批推荐默认，不是 PDF 原文；到期后须重新审阅，不偷偷延长。paused、max_runs=1、截止时间不超过原生确认时刻＋600 秒必须由仅手动的原生入口强制校验，实际 POST 复核同一确认、授权和期限；不得借用旧多次/长期 grant。行动许可还受当前会话授权及生命周期限制，不能承诺十分钟内必然发送。

确认框提供“取消/确认并运行一次”，默认安全取消。显示内容、三类“运行于”和明确的目录语义；受管目录不冒充用户书签，已有聊天必须来自授权列表，受限草案会话不可作为执行目标。新手动执行不改变计划 paused 或自动下一次时间，不触发自动启用。

复用原 grant→manual 两步事务，单次用户确认允许按顺序提交这两个明确步骤；每步使用独立且稳定的 request ID。若任一步回执不明，停止后续步骤并只读查证；查询成功不自动续发。明确重试保留原请求及内容，重试命中旧 run 只返回事实，不补建行动许可。正常权限刷新不能重发；scope/撤权不跨边界保留可提交内容。grant 已查证成功、且当前仍能证明 manual 从未发起时，UI 提供“继续本次运行”，用户再次明确点击后沿原 manual request/payload 提交并重验当前确认、版本和期限；这是原命令的显式提交，不新增继续/重发协议。manual 已观察到 run 只查看原运行；是否尝试仍不明则继续查证或显式同请求幂等重试，不补建行动许可。确认或期限失效后关闭原意图，回到重新审阅；不得用查证、旧回执或重试续期、增额。

原生新增**仅手动**的准入模式，能力查询和实际写入口保持一致：本批拒绝 enable、rerun，以及自动/重跑出站；保留现有 `native_schedule_tick` 的只读恢复与观察，只不装配自动触发资格及 `schedule_trigger_lifecycle`；不能为关自动而删除手动恢复循环。读取旧记录不受影响。当前显式新建 manual 请求在组合事务成功后取得一次行动许可，绑定本次原生确认产生的 grant、当前 UI context/revision、native scope、Host generation、生命周期 epoch、request/run 与原 create→turn 两个 operation。claim、Host 准备完成后的实际 POST 前再次验证。保存计划、确认 grant、读取回执、重新打开应用均不能生成发送许可。

`max_runs=1` 约束一次 run 的预约，不等于一次 Provider 请求。Ask 任务可能包含多次推理请求；实际 Provider HTTP 计数另行硬限制，不能把运行额度当费用上限。当前 run 已预约的最后一次额度仍可完成自己的 create→turn，不因 grant 显示 exhausted 被误拒，也不重复扣额。暂停/删除/版本变化、目标无效、并发占用、权限/期限失效继续沿原 worker 原子裁决；前台 queued、创建中、待审批及未释放 unknown 都算占用。

## 5. 许可失效与恢复必须闭合

不能只禁止出站而把用户永远困在排队或预约占用中。复用既有生命周期与恢复 owner，仅补本批激活所需的边界：

| 已知事实 | 必须行为 |
|---|---|
| create/turn 均证明从未尝试 | 许可或生命周期失效后，沿原 `cancel_unsent_schedule_reason` 原子取消、一次退款、quiescent 及预约释放；不再发送。 |
| create 已尝试或确认，turn 未发送 | 不适用 never-sent 退款。保留 unknown/未执行事实；正常退出记录原进程停止证据，重开只读恢复后按证据解除占用，不造成功/失败。 |
| turn 已尝试或已受理 | 只读查询原操作、观察原生事实；不因租期、查无记录或 Runtime idle 重发。实际进行中的任务沿原生中断；不能将关闭弹窗当取消。 |
| 映射尚不明，但有可信原进程正常停止证据 | 校验原 create generation、operation 和 attempt 后，复用 stopped 释放语义；不得只因新 nonce、404 或超时解除。 |
| 停止超时或证据不足 | 保留原 owner、STOP_PENDING 和 unknown，显示可刷新/正常退出的说明；不强杀、不退款、不删除预约伪造终态。 |

源码指出两处需要窄修正：`application.rs:2525–2574` 当前仅在 session 已找到时进入 stopped 释放；`recovery.rs:416–429` 可能因 grant 尚有效把失去行动许可的旧 turn 误认为仍可继续。需要考虑当前仅手动许可已失效，并补精确正常停止证据下映射缺失的分支。沿 `ChatRuntime::shutdown_for_app_exit` 记录 stopped generation 的既有流程，不新增生命周期管理器或“继续/重发”命令。释放仍同步处理聊天唯一索引与占用查询，保留历史事实。

## 6. 结果与交互闭环

- 按 native capability 决定按钮是否可用，说明缺资格、目标不可用、忙碌、过期、授权耗尽等原因。执行错误单独映射，不能沿用“是否保存成功/暂不能删除”的管理文案。
- 回执受理后定位同一 run，展示原生排队、运行中、待审批、已结束、失败/中断或未知。计划状态和运行状态分开；turn completed 不直接标业务成功，业务结果仍未评估。
- 最小详情包含历史名称/内容快照、触发方式、目标、投递和原生结果、安全错误及关联；执行时钟没有证据继续显示未知/未开始，不用 created_at/updated_at 推算。
- “查看完整对话”使用 native 返回的 conversation_id/local_turn_id；先验证本 scope 的原关联，再沿原 ChatPage、native history 和有界加载定位。深链参数不授资源访问或发送权限；目标轮未加载时明确加载/缺失，不能滚到最新轮冒充定位。缺少必要定位事实时可补同源私有只读叶类型，不新建历史存储或无限遍历。
- 审批和停止沿 FEAT-152 现役原生路径与原聊天操作，绝不恢复 FEAT-137 页面/协议。旧原生阶段缺失、partial 和历史未知保持真实语义。
- 沿用 Naive/Yj 与 2.1.0 tokens；局部 loading、默认取消、键盘/焦点、亮暗主题和最小 1180×760 窗口可用。此批“启用”“重新执行”继续禁用，页面文案须准确区分“可手动运行”和“尚未开放自动”。

## 7. 验证、调用预算与停止条件

当前真实文本累计 **4/12，剩余 8 次**；4B 上限曾由 3 增到 5，实际只用 4，不能把未用的一次再加到总额。建议本批最多使用剩余额度中的 **3 次真实 Provider 请求**，失败/中断及模型续接都按实际 HTTP 请求扣账；不要求用满，完成后至少保留 5 次。图片、商家、MCP 外部调用保持 0。4B 计数文件封存保留，新批 ledger 明确起始累计 4 与本批上限 3，禁止清零累计历史或退回直连；缺少硬计数通道时不开始真实调用。

先完成零调用检查：私有源 schema→生成 Rust/TS→strict conformance；原 SQL15、候选23重开和旧聊天；仅手动写入口/claim/POST；三目标、原请求重复、grant/manual 分步不明、忙碌、正常授权到期、正常停止/重开和 unknown 预约释放。用正常临时库与声明式本机 Provider，明确与真实证据区分，不做强杀、权限故障、攻击资源或二进制替换。

然后用固定候选 Runtime＋真实 Host＋本机声明式 Provider，证明普通 Ask start/turn/resume、原生终态、共享计数路由及请求/流重试策略符合限额；核对有效 `on-request/user/workspaceWrite/networkAccess=false`、固定产物与受管配置，以及没有图片/商家/MCP 外部配置继承，不能只看 HTTP 200 或 prompt 承诺；草案资格和过去普通路径测试不能代替这一步。资格失败先定位，不消耗模型做探路重试。

三项已有 ChatPage 显示断言继续单列历史基线；增加本批 native 运行状态和精确定位检查，若实际阻断使用则只修直接相关链路，不扩大为聊天重构。定向构建/测试、实际 UI 与真实 Provider 证据分别记录，最后做独立于实现步骤的源码/范围审查。
