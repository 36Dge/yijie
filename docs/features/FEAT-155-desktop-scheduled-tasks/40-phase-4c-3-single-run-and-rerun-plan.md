## 3. 最小数据决策与唯一源

本轮仅文档，`contract-impact=none`：未改变可执行代码、持久数据或wire。未来实现按 **breaking保守审查**：私有重跑预览/授权语义调整、新持久解释及准入改变需同步reader与consumer，不能因共享JSON形状复用就称无影响。

**推荐新增最小候选SQL25，明确区分“计划授权”与“本次运行授权”。** 当前表没有可靠的授权用途事实，不能用“没有enable回执”“max_runs=1”或计划是否指向该grant来猜它是新单次授权。

- 继续使用`chat_scheduled_grants`保存scope、计划revision、native授权revision、配置/目录摘要、次数、已占次数和期限，不复制额度或新建授权主库。
- SQL25仅新增一个以grant为键的单次授权用途关联，记录可识别格式版本、manual/rerun用途，以及仅rerun必需的原run引用；通过原grant及原run核对scope/计划。它是用途证明，不是另一份bearer或额度账本。
- 旧grant无新关联，保持旧解释；不得回填、新增许可或把历史rerun激活。当前已确认自动grant继续以SQL24原enable证明及计划指针约束，不借本次迁移续额。
- 新单次grant有明确用途证明，绑定审阅时的当前计划revision、配置及目标；**不写计划的authorization_ref/authorization_expires_at，不改state、revision、schedule_epoch、next_at或自动槽，不清future_hold**。授权1次，最长确认时刻+600秒，并继续受当前UI行动许可期限限制。
- 单次grant状态查询、准备、claim与实际POST必须按已知用途核验，不能全局删除计划授权指针检查。只有新的已知单次证明允许不等于该指针；旧manual保持旧限制，automatic仍要求指针相等。
- 新用途未知版本拒绝相关执行，保留数据和可解释历史；旧run/snapshot/trigger fact读取不能要求它必须具有新用途关联。已存`RerunConfirmation`格式和历史摘要保持，preview的新review类型不得改写旧confirmation_json。
- 先实现SQL25兼容reader，再显式允许隔离候选迁移/写入；普通入口仍SQL15/Host5，候选Host6不变。合成SQL24→25、旧manual/automatic/rerun、旧回执、聊天及正常重开必须通过。日常库不迁移，旧migration不改。

预计只改 Desktop 私有schema/生成物、原生存储与执行、页面及相关文档；元仓记录方案/报告。共享`PlanDefinition/PlanView/GrantConfirmation/GrantView/RunView`继续引用Contracts唯一源。Host wire、Runtime、产品依赖、平台权限及公共服务均不增加。私有用途封套由Desktop schema定义，不复制共享DTO；若实施证明共享域本身必须改，先列出实际差异再按Contracts唯一源处理，不能夹带扩展。

SQL25比仅解锁按钮多出一个兼容步骤，理由是旧授权确实无法表示“独立单次、不接管自动计划”。采用进程布尔开关或从缺失记录推断用途会使重开后的读取、历史授权和实际发送解释不一致，不推荐。

## 4. 预览、确认、请求与发送

### 4.1 只读审阅

重跑预览只要求当前scope读取权及真实原run，返回原运行时`PlanDefinition`、当前已保存`PlanDefinition`，以及原run/快照摘要、plan/revision/当前配置摘要。它不要求plan有grant，不准备Host、不创建目录、grant、run或outbox。原计划已删除拒绝；未执行的槽/跳过记录没有原run，不能包装成重跑，应引导到当前计划的立即运行。

审阅覆盖名称、内容、频率/时区和运行目标变化；授权ID、剩余额度和状态不是内容差异，但另行显示当前状态及本次许可。已有聊天显示可信标题/标识与目录语义；每次新建聊天明确会生成不同会话，专属聊天沿当前有效关联，不能为了重跑找回已删除聊天。旧聊天缺失不等于必须拒绝全部重跑：当前目标仍有效且用户明确确认时可按当前目标运行；当前目标本身缺失则拒绝。

### 4.2 复用两步许可，不隐式续额

保留已验证的“明确一次确认→单次grant→原组合运行事务”交互，两个阶段分别持稳定请求ID。新增私有单次授权封套复用`GrantConfirmation`，附manual/rerun用途及rerun review。原生在授予时核对当前配置和原run，在组合提交时再次核对；先把grant成功解释为已运行是错误的。

- 立即运行提交当前计划及revision；重跑提交原run/快照和当前配置摘要。用途、review、期限与次数参与新的幂等摘要，同ID换用途/原run/内容须冲突。
- 新grant与用途关联同事务保存；目录准备仍在运行事务外幂等完成，不宣称文件系统与SQL原子。run、原聊天/turn/outbox、预约及该grant一次扣额沿原组合事务一起提交。
- 新rerun使用新run、新request、新operation，记录`original_run_id`及新快照；按当前三目标策略创建或关联对话。原run、原快照、原终态和旧outbox不覆盖、不翻转，也不把新结果写回旧记录。
- 同一grant只允许所绑定的manual或指定原run的rerun，不能交换来源借用。每份新grant最多被一个未退款运行占额；重试同一请求返回原事实，不再创建、扣额或更新行动许可。
- 扩展执行回执的rerun只读分支；单次grant查证同时明确其用途。`not_observed`不证明未提交；不自动换ID。只查到grant且运行从未提交时，仅用户明确继续且原行动许可仍有效才能进入下一步；正常重开、过期context或Host换代均不得从持久回执重建许可。
- 新鲜许可要求当前执行权限及同一UI context、Host nonce、process/epoch、plan revision和期限；确认、预约、claim、Host准备后create/turn实际POST各自核验。实际POST的非automatic Host检查继续保留。

### 4.3 自动与单次执行相互独立

已开启、已暂停、仅一次已完成计划均可申请单次运行；deleted/无权/目标失效拒绝。自动授权到期、耗尽或缺旧自动确认本身不授单次资格，但用户可以另行明确授权一次；不能清理自动hold来“修复”单次执行。已完成once的单次执行不会重新开启计划或产生未来时间。

单次授权与准备事务自身不更改自动计划/额度。它运行期间，如果独立自动tick到点，仍按原全局最多一个定时运行及同聊天占用规则记录忙碌跳过并推进未来，不排队补跑、不扣自动额度。这种正常调度变化应区别于单次事务偷偷修改计划，测试要分别证明。

暂停/编辑/删除/native撤权或目标变化后，新POST需重验；尚未尝试的运行可以取消，已开始的只能继续观察或由原生中断，暂停不假报已停止。立即运行/重跑结果不确定仍设置必要的unknown安全hold，不能为了“计划不变”删除安全保护；可信释放也不自动清hold。

## 5. 恢复、并发与UI收口

- 扩展现有当前进程行动许可，覆盖manual/rerun并绑定用途/原run；不建立第二个执行管理器，不关掉`manual_runtime.enabled`作为解锁方式。
- `expire_unstarted_rerun`改为按本次有效许可判定；有效新rerun不能被4C-2历史清理直接取消。失效完整never仍按原事务取消/一次退款/预约及聊天占用释放；create或turn已尝试则不退款、不POST。
- native启动仍区分未来有效自动意图与待收尾运行；仅有单次授权不启动后台发送。重开可只读恢复或安全清理旧single run，不能获得一次新的执行机会。旧manual和automatic正常路径均回归。
- 全局/同计划/同聊天预约继续覆盖前台queued、creating、审批及unreleased unknown。重跑不是解锁unknown的手段；必须先取得原生终态、正常中断或精确正常停止证据。已释放但历史仍unknown可经警示明确重跑，旧结果继续未知。
- 管理和记录页面复用已有Naive/Yj确认与结果定位。重跑显示“使用当前已保存配置”及原/现差异；无差异明确说明；已删除计划、未执行槽、目标缺失、忙碌、权限拒绝都有准确禁用原因和可行出口。
- 更正现有单次成功提示中的“计划仍保持暂停”，按实际状态呈现。本次受理不等于原生完成或业务成功，结果卡沿新run定位新conversation/local_turn，旧结果仍可打开。
- loading仅限制冲突操作，取消不授予许可，默认焦点取消；已发送后不假撤回。未知保留原意图，提供查证/原payload明确重试；scope变化清UI意图，权限刷新不续期。确认框内部滚动、亮暗/1180×760和键盘检查沿现有规范。
- 本批不重做聊天显示、不填造phase或历史时间，不顺带重排整个管理页；AC-006其余图标细节和全部Must仍按最终完整核验判定，不能仅凭新按钮接通关闭整个AC。
