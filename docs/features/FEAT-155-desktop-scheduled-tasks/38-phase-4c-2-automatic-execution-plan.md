## 3. 契约、最小存储决策与回退

本轮文档 `contract-impact=none`：没有改变可执行行为、持久库或跨仓 payload。未来实现按 **breaking 保守审查**，因为收紧旧候选自动授权解释、新增跨版本持久字段并改变原生装配，不能仅按新增 UI 判断为 additive。

预计产品变更仅 Desktop；元仓记录设计和交付。Host、Contracts、固定 Runtime 先复用已验证产物和共享契约，不新增服务、公共 Host 方法、模型通道、依赖或 Runtime 补丁。Desktop 私有 IPC 源 schema 先行，生成 Rust/TS、resolved schema 与严格校验一起更新；复用现有 GrantConfirmation、GrantView、PlanView，不复制共享 DTO。若发现确需修改公共 wire，先明确唯一源和具体差异，不能夹带实施。

私有 enable 确认封套复用共享 GrantConfirmation，并增加用户已审阅的 `expected_next_at` 比较值。native仍自行计算时间，在同事务中比对；不一致返回冲突并要求重审。新字段参与新启用请求的幂等摘要，不能同ID换预览继续提交；明确区分原有enable摘要与新确认摘要，旧记录和原请求只读可查，不能靠兼容解析补实际自动资格。新写入口缺该比较值时拒绝，不以renderer提供的时间替代时间权威。共享确认类型及Host/Runtime wire保持原定义。

**新增职责决策：实际自动确认的持久证明。** 推荐 SQL24 仅对 `chat_scheduled_enable_receipts` 追加可空 `automatic_consent_version`，NULL 表示历史候选确认未取得现役自动发送资格，当前已知版本 1 表示经新原生确认入口作出的有限自动授权。语义版本由 native 决定，不允许 renderer 自报。其余 plan、revision、native authorization revision、definition/workspace、次数、期限继续引用原 grant，不能新建另一份计划或额度主状态。

- 不改 SQL21 或旧迁移，不把 format_version 从1伪装改成2；现有 CHECK 不允许这样写。新字段未知版本只读保留、拒绝发送。
- SQL15 和既有候选16–23按各自支持边界读取；SQL24先兼容读取再允许写入。存在旧SQL23库不等于获得升级日常库许可，本批只用明确隔离的候选/临时库。
- 新鲜 enable 请求在同一事务保存最终 revision、有限 grant、enabled、未来槽、旧格式回执以及 consent=1。只有当前有效 UI 确认、当前 native 权威、实际候选资格均满足，才可写该标记。
- 旧 enable 原请求重放只返回原回执及当前事实，绝不补标、续额、清 hold 或复活暂停计划；历史 grant 不因格式升级或正常重开取得资格。旧 enabled 无标记时有效状态为需重新确认；用户可暂停，或使用新 request 审阅当前配置后重新确认。新确认需沿原事务替换旧授权，不能因 raw enabled 的旧冲突判断把用户卡死。
- 后台仅接受当前计划所指 grant 的已知 consent；标记本身不是 bearer 或独立权限，还必须通过每次 native/目标/期限/额度/连续性校验。暂停、编辑、撤权或版本变化沿既有规则使原授权不再可用于新投递。
- 标记约束未来资格和发送，不加入历史 read_run/validate_facts 的完整性要求。旧 automatic run 仍可只读查询、恢复观察和依据可信证据释放，不能因缺新标记变成格式错误或伪造终态。
- 旧 consent=NULL 时，列表、详情、筛选、能力和启动判断使用一致的有效状态。不能卡片显示开启而原生永远拒绝。保留原始历史，不靠写坏旧状态达到禁发。
- 回退先关闭新确认与新claim，正常停止既有受管进程，保留SQL24/Store6兼容读取和历史；不得让SQL23旧binary写SQL24、降级schema、删除新列或恢复副本覆盖现状。

普通 **SQL15/Store5** 保持；候选 **SQL23→24/Store6** 是本方案明确新增的最小兼容成本，不扩展执行时钟、通知或其它存储。兼容检查要包含旧 enable 回执、manual 回执、旧聊天及正常重开，旧 INSERT 的位置参数也须同步改为明确列名，不能只加列使既有写入失败。

只读查询推荐扩展现有执行回执操作中的 enable 分支：scope＋原 request ID，验证 enable_receipt 已知格式并关联原 grant，返回原确认是否观察到、其实际自动确认资格以及当前 plan/grant/hold。查证不准备 Host、不授予许可、不新建 run。`not_observed` 仅表示未观察到，不能推定未提交或自动换 ID 重试。

## 4. 自动权限与原事务

以明确的逐触发准入替换“关掉手动模式就开放全部”的路径；不得将允许自动设置成绕过共用 guard 的全局布尔开关。

| 来源 | 现役准入 |
|---|---|
| manual | 保留4C-1：暂停计划、原生最多1次/最长10分钟、当前 UI/Host generation/lifecycle epoch/action permit、原 create/turn 身份；重开、查询和旧请求不补许可。 |
| automatic | 当前计划已显式自动确认的持久有限 grant；每次新建的 native authority；正确计划版本、目标、目录和 Ask；当前进程/epoch连续性票据及原槽60秒窗口。 |
| rerun | 写入口、claim、实际POST均拒绝，保留旧只读历史和基础代码供后批使用。 |

自动在到点组合事务、claim、Host准备完成后的实际 create/turn POST 前分别复核。已预约的最后一额允许完成本次原 create→turn，不因 grant exhausted 或 budget hold 误拒；不能二次扣额。background 不持有 renderer bearer 或过期 context，UI刷新或导航离开不等于撤销持久有限授权；真正 native 撤权、期限/版本/目标失效仍阻断。

沿原触发事务处理槽、run、目标懒绑定、原 outbox、一次额度与严格未来 next_at。目录准备仍在事务外幂等进行，不把文件系统和SQL假装成原子事务。相同槽及重复tick不会新增第二份运行；不建立新队列，不把忙碌延迟成以后补跑。全局最多一个定时运行以及同计划/同聊天占用，继续覆盖前台排队、创建中、待审批和未释放 unknown。

对 manual 清理、automatic 清理和恢复的原许可判断逐一分流：完整 never 才沿现有取消/一次退款/quiescent/预约释放；create已尝试或turn已尝试则只读恢复、不退款、不重发。解除 unknown 占用必须有原生终态、正常中断或精确正常停止证据，且不自动清除 future_hold。释放同时更新聊天唯一索引与占用投影，不能删预约或伪造终态解锁。

## 5. 原生启动、时间与停机

本批明确承接**正常重开后未来自动计划恢复**。将启动准备放在现有 native App/ChatRuntime 生命周期内：

1. 在已选择的隔离候选数据目录，按当前native scope分别判定两种启动原因：A为已知consent、enabled、仍有期限/额度的自动意图；B为未收尾scheduled run或待清理预约。不能仅按旧 `next_at > now` 筛A，循环计划离线后仍须先有界恢复未来时刻。预算耗尽、过期、unknown hold或缺新consent不能使B被遗漏；B只允许恢复/清理，绝不授予旧run发送权。普通入口、仅保存/手动grant和无意图亦无待收尾记录的场景，不因管理查询启动执行链。
2. 先完成可在本地证明的安全清理；A需要执行准备，或B确需Host只读事实时，沿原 sidecar/Runtime readiness、原 application 和唯一 Coordinator 装配。仅B时保持新发送关闭，不能借恢复顺便给旧计划/普通未发送消息授予新权限。首次启用由显式“准备并审阅”完成同一准备过程。原生启动没有 renderer context，不伪造管理/执行 UI 授权。
3. 关闭新发送资格后，以新的process/epoch和恢复截止点独立进行有界时钟恢复与有界旧run观察。旧run未知或Host未ready不能阻断计划时间推进；持续占用继续阻止新投递，不能等unknown变终态才恢复时间。仅在所有恢复/权限/资源和连续性条件具备后允许未来新槽。旧manual无新许可，旧automatic的旧连续性票据失效，旧rerun仍禁止；不能自动续投任何旧run。
4. 凭据/固定产物/Host准备失败时保留可读计划及具体不可执行原因，提供用户显式重试准备；不能在50ms循环中无限拉起Host。不存在可投递run时，准备与只读恢复不得产生Provider请求。启用事务已成功但随后的readiness丢失，要如实显示计划与当前设备条件，不假报未保存或自动换ID再确认。
5. 正常退出、睡眠和时钟不连续先关闭新发送资格；恢复后只算未来。关闭窗口若导致App退出则停机；App仍运行且设备清醒时，页面隐藏/导航变化不停止有效自动计划。正常停止超时沿STOP_PENDING保留owner，不强杀。

管理读命令继续保持无Host启动副作用；原生启动策略独立于管理页面是否打开，不能靠renderer轮询保活。新装配必须满足原Coordinator admission和既有事件桥/身份约束，不另建Coordinator绕过它。

保留[19方案](19-phase-3c-2-implementation-plan.md)的时间语义：四频率、固定IANA时区、DST重复一次/缺失跳过、有界计算；连续清醒时仅原计划时刻后60秒内可首次发送，create和turn各自发送前均检查；重开、睡眠或时钟跳变跨过的槽不因仍在60秒内而补跑。忙碌槽记录未执行原因并推进、不扣额、不伪造run；长期离线有界压缩，不逐日无界遍历。仅一次完成以原生终态或明确未执行的调度义务结束为准，循环单次完成不能把整个计划置completed。

## 6. 确认与状态交互

两种创建方式本批仍先保存暂停计划，再单独确认自动启用，不把保存成功与自动授权合并。确认弹窗显示当前名称、内容、运行目标/目录、Ask、时区、下一次时刻、最大运行次数和绝对截止时间；同时说明此设备的易界运行且电脑清醒才执行、退出/睡眠不补跑、需要批准时去原对话处理。

推荐默认次数 **1**，允许用户明确填写已有契约支持的有限正整数；不新增“无限运行”。截止默认 **native计算的下一次时刻＋10分钟**，可明确调整，UI展示其实际日期和时区。该默认是本方案建议，不是PDF原文；它给默认的一次授权留出发送时间，不承诺覆盖多个周期。对多次授权提示“到次数或截止时间先到者为止”，不能把次数当作未来一定运行的承诺。若时间接近支持上界而无法产生有效默认，要求用户调整计划/截止，不溢出或猜值。

原生在提交时重新计算未来 next_at，拒绝无未来时刻或 `expires_at <= next_at`，不能只信旧预览。重复计划的旧next_at可能已过时，应调用原生时间预览后审阅，将其作为私有 `expected_next_at` 提交；同事务重算不一致则要求刷新重审。前端再次预览不能替代原生比对。原子回执显示真正保存的下一时刻，启用不承诺设备必然准点执行。仍用一个稳定 enable request ID，同事务提交新版本及授权，不先grant再enable制造额外两步许可。用户取消不创建授权；已发出后关闭不等于撤回。

回执不明时保留原意图并只读查证，明确重试只用同ID/原payload；查回旧回执展示“原确认已记录，当前计划状态为……”，不一律显示已开启。参数/版本冲突回到新审阅，不偷偷改变原请求内容。读取、自动权限刷新、重新进页面和正常重开都不能续额。持久授权耗尽/到期/unknown或旧候选未确认时，提供重新审阅入口；未解除占用时仍拒绝重新确认。

卡片与记录遵循同一有效状态：已开启、暂停、仅一次已完成，以及授权到期、额度耗尽、目标/资源不可用、结果未知、需重新确认等原因。现有详情grant字段用于呈现真实次数、占用和截止；不要维护前端第二账本。raw enabled但有效暂停可以明确暂停；普通“暂停”与重新确认分开，不清理未知历史。暂停与POST竞争按原子序列处理：尚未获准发送则阻断、已尝试/受理则观察并沿原生中断入口，不能假称终止正在运行的一次。

本批不放宽4C-1“手动仅暂停计划”边界：已开启计划的立即执行应禁用并说明先暂停；有效暂停而raw enabled时也提供明确暂停操作，不静默改变计划后发模型。该过渡限制及完整立即执行/重跑语义在后续批次审阅，不据此标完整AC-006通过。

结果复用既有执行记录、原生审批/中断和精确 conversation/local_turn 定位；未执行槽只显示未执行原因，不造聊天或成功结果。业务成功未评估、缺执行时钟和Provider缺phase继续如实呈现，不扩大为聊天显示重构。沿用Yj/Naive与2.1.0主题、默认取消、局部loading、键盘焦点及1180×760最小外框。
