## 3. 按依赖顺序执行

以下是同一第二阶段内的工程步骤，不新增治理切片，也不自动进入第三阶段。

### 步骤一：先验证时间库，再固定时间语义

1. 审核并精确锁定rrule候选及实际依赖/TZ数据来源，在独立纯时间测试中核实API和行为；仅安装/构建本项目可复现依赖，不启动应用。
2. 使用现有草案schema中的结构化时间规则作为输入形状依据：仅一次、每天、工作日、每周所选日、IANA时区和分钟时刻。对外不增加任意Cron/RRULE入口。
3. 统一native evaluator，提供给未来预览和触发共同使用：重复计划查询严格未来时刻；仅一次保存经校验的UTC instant及原时区表示。夏令时重复取较早UTC一次，不存在的当地时刻跳过并返回原因。
4. 用明确参考时间与有限查询范围计算，验证长时间离线不会从最早创建时刻无界遍历。不能用all_unchecked，不能只截断输出就宣称计算有界。候选不满足要求时记录具体失败并重新选择成熟接口，不手写DST/RRULE引擎。
5. 将已批准的60秒连续清醒延迟、不补跑、墙钟变化规则实现为可注入时间参数的纯判断；本阶段不接timer或系统sleep/wake事件，真实连续清醒证明仍由第三阶段提供。不能根据这些单元测试声称实际睡眠恢复通过。

完成条件：正常频率、跨日、闰日、DST fold/gap、固定时区和长期离线边界都能给出可判定结果；规则版本和实际依赖来源可追踪。尚未验证前不开始依赖该算法的计划writer。

### 步骤二：冻结本阶段最小契约与数据边界

Contracts只定义本阶段将被消费的计划定义/管理结果与时间预览结构，以及稳定错误（输入无效、revision冲突、目标不可用、存储未启用等）。复用第一阶段草案的时间/目标意图权威，使用引用或同源投影，避免复制后独立演进。

- `plan_id`、`revision`、`schedule_epoch`、owner/tenant scope分别定义；scope取native权威，不接受模型或renderer自授权。
- 三模式保留：专属新聊天、每次新聊天、已有聊天。已有目标使用**本地conversation ID**，不是Host session ID；原生身份在第三阶段执行后关联。新聊天仅保存native受管来源意图，本阶段不创建目录/聊天、不解析成首个用户项目。
- `revision`用于编辑并发控制；只有改变时间解释的变更更新`schedule_epoch`。时间编辑从保存之后的未来生效，不能靠改epoch恢复过去已消费时刻。
- 为后续有限授权保留可空的native授权引用及期限语义，不接受模型授予额度；没有有效执行授权只可保存暂停计划。真正启用、额度占用和请求计数留第三阶段，本阶段不实现虚假“已开启并可运行”。
- 需要的Rust/TypeScript wire投影由独立leaf工具生成并做同源conformance；私有SQL表/内部类型仍归Desktop。第一阶段Host查询契约及历史generator/consumer pin保持。

不注册新的renderer可调用写入口，不接页面，不扩大为计划平台API全集。保存和预览先由native领域服务及定向测试验证，后续接入时再落实对应Tauri command/capability。

### 步骤三：兼容reader先行，普通入口不自动升级

1. 分离“本候选能够理解的最高schema”与“此次允许迁移到的目标schema”。按当前catalog，新增版本候选为16，实际开工时复核编号。
2. 默认日常入口的目标仍为15，不能因为增加catalog条目而自动to_latest到16。只有明确启用的阶段验证入口在全新正常合成临时SQLCipher库中前向验证15→16；不复制日常库、不使用用户Keychain数据。
3. 兼容reader核验完整migration ledger/checksum和新格式；不修改1—15的SQL或已存hash，不只抬高版本常量绕过校验。已是16的库不得因目标15降级；未知更高版本继续拒绝。
4. 新版reader在正常合成数据上验证旧聊天读取/操作与新计划记录共存；关闭计划writer后仍能读取，且普通入口不会为15库提前创建计划表。错误保留原文件与原状态。
5. 本阶段只形成源码候选、可复现检查与兼容证据，不启动canonical日常应用验证新schema。原schema-15旧binary不能作为16库的回退；最终允许日常writer前还需确保真正的兼容候选来源可恢复并覆盖第三阶段新增格式。

### 步骤四：在同一worker实现计划和occurrence基础

最小持久对象：

| 对象 | 本阶段保管的事实 |
|---|---|
| Plan | scope、plan_id、revision、名称/内容、结构化规则/时区/版本、目标意图/引用、暂停等生命周期、next UTC、生效边界、可空native授权引用 |
| Occurrence | scope、plan_id、schedule_epoch、logical_slot、scheduled UTC、本地调度判定及错过原因；不标原生成功/失败 |

实现scoped保存/读取/编辑/暂停/删除及下次时间更新；重复确认使用稳定请求身份去重，编辑必须带expected revision。读取/写入继续使用ChatScope，跨scope不返回记录，不通过标题猜身份。

自动槽唯一约束为`(owner, tenant, plan_id, schedule_epoch, logical_slot)`；logical_slot表示当地日历时刻，DST重复不生成第二槽。计划更新与本地时间推进处于同一事务；正常重开不补出历史执行，长时间离线只记录有界错过区间，不生成海量run。

**本阶段不提供可供调度器使用的独立claim/投递事务。** occurrence存储和唯一键可独立验证；第三阶段才把claim、授权占用、本地会话/run与既有outbox放进同一事务。不能先落一个“已claim”记录，再异步拼接outbox并声称原子。

必要的删除保护也在本阶段完成：删除被已有/专属模式引用的聊天时，同事务暂停计划、清除可恢复目标关联并记录无正文的target_missing；每次新聊天模式不因某个历史聊天删除而停用未来计划。删除计划不级联删除聊天。尚无run/outbox的本阶段不实现未来在途协调；该部分随第三阶段组合事务一起补齐。

## 5. 检查与完成标准

只使用正常合成临时数据、既有正常接口与可注入的时间参数；不用强杀、故障/攻击注入、权限破坏或运行时替换。

| 检查组 | 判定标准 |
|---|---|
| 来源与契约 | 源/生成物一致，字段/未知输入/错误conformance通过，旧族及阶段一来源无无关变化 |
| 时间 | 四种频率、IANA校验、DST、跨日/闰日、固定时区、未来边界、有界长期离线计算；正常延迟与恢复不补跑的纯判断符合既定语义 |
| 持久与并发 | 正常保存/重开一致；重复确认、revision冲突、同槽重复、时间编辑生效边界、暂停/删除均有明确结果 |
| scope与目标 | 原native scope隔离；三目标可表达；不存在/删除目标暂停且不换目标，计划删除不删除聊天 |
| 兼容 | 默认15不升级；合成15→16正常迁移/重开；完整ledger及旧聊天保持；兼容reader可读；未知版本拒绝；无down migration |
| 零执行副作用 | 没有可消费的新增outbox、实际会话创建或Runtime/Provider调用；普通入口未激活计划writer |

按实际改动运行独立契约generate/lint/test、Rust fmt/clippy和已审查定向测试，补必要旧聊天回归；历史含禁止fixture的全量测试明确跳过并记录影响。每项只按实际结果写PASS；本阶段全部通过仍不代表AC-001—010或D4通过。

计划工作量参考6—10小时，不作为硬停止；时间库不满足要求或出现既有兼容缺口时先记录事实并调整本阶段最小方案，不借机扩大功能范围。
