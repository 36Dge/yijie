# Kimi K3.1 Pro 默认推理强度调整

2026 年 11 月 21 日，易界将新对话和新计划使用的 Kimi K3.1 Pro 配置设为 `high`。模型 ID 仍为 `kimi-k3.1-pro`，上下文窗口为 1,048,576 tokens。

## 影响链路

| 环节 | 行为 |
| --- | --- |
| 模型选择 | 模型契约 0.3.0 将 `kimi-k3-1-pro-high-v1` 设为默认配置。新建聊天、新建计划和丢弃草稿后的模型选择都读取同一默认值。 |
| 请求发送 | Host 将选定配置的强度传给原生线程和回合。普通聊天、专家、标题、计划草拟以及读取工具结果后的续答沿用这条链路。普通、原生工具、工具搜索三份 Runtime 模型目录和受管 TOML 都支持从旧配置升级。 |
| 历史和重试 | `kimi-k3-1-pro-max-v1` 继续代表 `max`。既有会话、已接受的请求和回执保留原档位。打开已有计划时使用其保存的配置，绑定聊天的计划使用该聊天确认的配置。更换已授权计划的模型须经原有审阅和重新授权流程。 |
| 本地存储 | SQLCipher 迁移 49 在同一事务中扩展五张表的模型标识约束。原模型选择、操作快照、计划、恢复回执和交付证明按原值复制。 |
| 跨版本 | 此次契约影响为 `breaking`。旧桌面端只接受两个配置项及旧默认值。桌面端和 Host 必须使用同一版契约，数据库升至 49 后须使用支持该版本的客户端。 |

契约在本机提交为 `05bbf1b59826ae67c33d4757ed6a34c6492478a7`。Go、Rust、TypeScript 和计划、专家及连接器校验器均由原生成流程同步。

## 验证

- 契约测试覆盖新默认、两种 Kimi 配置与各自强度的绑定、旧操作回放，以及计划、专家和连接器对新标识的接受。
- 桌面端测试覆盖新建、丢弃草稿后恢复默认值、旧会话继续使用原配置，以及新旧计划的保存。Native 使用临时数据库验证原值保留、新旧两档均能写入、重新打开及暂停 Kimi 后的计划派发。
- 真实 Codex Runtime 向本地 Responses 服务发出的请求中，观察到了 `reasoning.effort = "high"`。日常版 Runtime 的四个回合覆盖新建、连接器选择变化和冷启动恢复。已保存的 `max` 会话可在同一线程中切换至 `high`。

## 日常客户端启用结果

从原“易界.app”入口启动。启动前已保留日常加密聊天库的冷备份，待发送请求、未完成回合、待派发连接器请求、已启用的定时计划及待恢复的计划运行均为 0。

客户端通过构建校验，Host 和 Runtime 均返回就绪。运行中的模型目录返回默认配置 `kimi-k3-1-pro-high-v1`，强度为 `high` 且可用。三份受管模型目录和实际加载的 TOML 默认值也均为 `high`。

日常聊天库从版本 45 升至 49。逐行核对了五张模型相关表、聊天回合表及计划授权表，七张表的行数和内容摘要全部匹配，外键检查通过。启动过程中 Runtime 线程数保持 2，新增回合与 token 用量均为 0。付费模型调用 0 次。

## 提交前复核

- 独立 Kimi 构建入口的来源清单仍引用旧契约。用原生成脚本更新后，独立入口和日常入口的来源校验均通过，两份清单绑定同一个 Host 提交及相同的 707 个构建输入文件。
- 本地 Responses 模拟服务现按请求实际携带的强度记账。分别发送 Kimi `high`、Kimi `max` 和 MiniMax `high`，三次响应与记录均吻合，模拟服务正常退出。
- 原生存储测试在启用当前配置时使用 `high` 和数据库版本 49，同时保留旧写入流程的测试。通过普通聊天、连接器、专家、计划快照及恢复用例。界面用例确认新聊天菜单显示一项 Kimi `high`，已有 `max` 会话正确显示其档位。
- 再次比较数据库版本 48 和 49 的 128 个表、索引等结构对象，只有预期五张表增加了 `high` 可选值。19 项契约用例、前端定向用例、类型检查及 Host 原生回环复验通过。日常 Host 只读就绪检查返回 HTTP 200，默认配置仍为 `kimi-k3-1-pro-high-v1`。本轮复核付费模型调用为 0 次。
